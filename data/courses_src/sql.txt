## LESSON sql-01 | Database là gì? Cài SQLite trên Windows

### Database giống một file Excel lớn
• Database (cơ sở dữ liệu) là nơi ứng dụng cất dữ liệu lâu dài: người dùng, đơn hàng, sản phẩm...
• Mỗi bảng giống một sheet, mỗi dòng là một "phiếu", mỗi cột là một loại thông tin.
• SQL là ngôn ngữ để "hỏi" database, ví dụ: "cho tôi xem tất cả user ở Vân Thoi".
• Tester dùng SQL để kiểm tra dữ liệu thật sự được lưu đúng hay chưa, không chỉ tin vào màn hình.
~~~text
File Excel "shop"            Database "shop.db"
- Sheet "users"         ->   Bảng (table) users
- Hàng thứ 2            ->   Một dòng (row / record)
- Cột "email"           ->   Một cột (column)

Bảng users:
id | full_name       | email            | city
1  | Nguyễn Văn An   | an@example.com   | Vân Thoi
2  | Trần Thị Bình   | binh@example.com | Mầm Rìa
~~~

### Khóa chính và khóa ngoại
• Primary key (PK, khóa chính): mã định danh duy nhất của mỗi dòng, giống số CCCD — không được trùng.
• Foreign key (FK, khóa ngoại): cột trỏ sang khóa chính của bảng khác. orders.user_id = 1 nghĩa là đơn này của user có id 1.
• Nhờ khóa ngoại, ta biết đơn hàng 1 và 2 cùng của anh An.
• Bug kinh điển: đơn hàng trỏ tới user không tồn tại (gọi là dòng "mồ côi" — orphan row).
~~~text
users                     orders
id (PK) | full_name       id (PK) | user_id (FK -> users.id) | status
1       | Nguyễn Văn An   1       | 1                        | PAID
2       | Trần Thị Bình   2       | 1                        | PAID
                          3       | 2                        | SHIPPED
~~~

## LESSON sql-02 | Tạo bảng và dữ liệu mẫu để luyện tập

### Tạo bảng users
Mở Notepad hoặc VS Code, tạo file C:\qa\sql\seed.sql. Dán lần lượt code của slide này và 3 slide sau vào cùng file.
Giải thích từng dòng:
• DROP TABLE IF EXISTS: xóa bảng cũ nếu có, để chạy lại script nhiều lần. Chỉ dùng trên database tập luyện của bạn!
• CREATE TABLE users ( ... ): tạo bảng tên users.
• id INTEGER PRIMARY KEY: cột số nguyên, là khóa chính.
• full_name TEXT NOT NULL: chuỗi, bắt buộc có giá trị.
• email TEXT: chuỗi, được phép để trống (NULL).
• created_at TEXT: ngày tạo, lưu dạng chuỗi yyyy-mm-dd.
~~~sql
DROP TABLE IF EXISTS orders;
DROP TABLE IF EXISTS products;
DROP TABLE IF EXISTS users;

CREATE TABLE users (
  id INTEGER PRIMARY KEY,
  full_name TEXT NOT NULL,
  email TEXT,
  city TEXT,
  created_at TEXT
);
~~~

### Tạo bảng products và orders
Giải thích:
• products: sản phẩm với giá (price, đơn vị đồng) và tồn kho (stock).
• DEFAULT 0: không nhập stock thì tự lấy 0.
• orders: mỗi đơn có user_id (ai mua), product_id (mua gì), quantity (số lượng), status (trạng thái).
• FOREIGN KEY ... REFERENCES: khai báo khóa ngoại trỏ sang users và products.
Lưu ý: SQLite mặc định KHÔNG bắt buộc khóa ngoại (trừ khi bật PRAGMA foreign_keys = ON). Ta lợi dụng điều này để tạo sẵn vài "bug dữ liệu" cho bài săn lỗi.
~~~sql
CREATE TABLE products (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  price INTEGER NOT NULL,
  stock INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE orders (
  id INTEGER PRIMARY KEY,
  user_id INTEGER,
  product_id INTEGER,
  quantity INTEGER NOT NULL,
  status TEXT NOT NULL,
  created_at TEXT,
  FOREIGN KEY (user_id) REFERENCES users(id),
  FOREIGN KEY (product_id) REFERENCES products(id)
);
~~~

### Thêm dữ liệu users
Giải thích:
• INSERT INTO users (các cột): thêm dữ liệu vào bảng users theo đúng thứ tự cột liệt kê.
• VALUES: mỗi cặp ngoặc ( ... ) là một dòng; các dòng cách nhau bằng dấu phẩy, dòng cuối kết thúc bằng ;
• NULL: không có giá trị (user 4 chưa có email).
Bug cài sẵn: user 5 trùng email với user 1. Trên hệ thống thật đây thường là lỗi.
~~~sql
INSERT INTO users (id, full_name, email, city, created_at) VALUES
  (1, 'Nguyễn Văn An', 'an@example.com',   'Vân Thoi',  '2025-01-05'),
  (2, 'Trần Thị Bình', 'binh@example.com', 'Mầm Rìa', '2025-02-10'),
  (3, 'Lê Minh Châu',  'chau@example.com', 'Lụa Mầm',  '2025-02-20'),
  (4, 'Phạm Thu Dung', NULL,               'Vân Thoi',  '2025-03-01'),
  (5, 'Hoàng Gia Huy', 'an@example.com',   'Sợi Nếp', '2025-03-15'),
  (6, 'Võ Ngọc Lan',   'lan@example.com',  'Lụa Mầm',  '2025-04-02');
~~~

### Thêm dữ liệu products và orders
• 5 sản phẩm, 8 đơn hàng.
Bug cài sẵn để luyện tập:
• Đơn 7 có user_id = 99 — không có user nào id 99 (dòng mồ côi).
• Đơn 8 có quantity = 0 mà vẫn PAID — vô lý.
~~~sql

  (2, 'Chuột không dây',  320000,  50),
  (3, 'Tai nghe',         1200000, 0),
  (4, 'Màn hình 24 inch', 3500000, 8),

  (1, 1,  1, 1, 'PAID',      '2025-04-10'),
  (2, 1,  2, 2, 'PAID',      '2025-04-11'),
  (3, 2,  4, 1, 'SHIPPED',   '2025-04-12'),
  (4, 3,  5, 3, 'CANCELLED', '2025-04-15'),
  (5, 3,  1, 1, 'PAID',      '2025-05-01'),
  (6, 6,  3, 1, 'PENDING',   '2025-05-03'),
  (7, 99, 2, 1, 'PAID',      '2025-05-04'),
  (8, 2,  2, 0, 'PAID',      '2025-05-05');
~~~

## LESSON sql-03 | SELECT và WHERE: hỏi đúng câu hỏi

### SELECT: xem dữ liệu
Giải thích:
• SELECT *: lấy tất cả các cột. Dấu * nghĩa là "mọi thứ".
• FROM users: từ bảng users.
• Dòng 2 chỉ lấy 3 cột cần thiết — nên làm vậy với bảng lớn.
Kết quả mong đợi dòng 2 (gõ .headers on và .mode column trước cho dễ đọc):
id  full_name      city
1   Nguyễn Văn An  Vân Thoi
2   Trần Thị Bình  Mầm Rìa
3   Lê Minh Châu   Lụa Mầm
... (tổng 6 dòng)
~~~sql
SELECT * FROM users;
SELECT id, full_name, city FROM users;
~~~

### WHERE: lọc dòng theo điều kiện
WHERE giống bộ lọc trong Excel: chỉ giữ lại dòng thỏa điều kiện.
Giải thích từng dòng:
• Dòng 1: sản phẩm giá dưới 500.000 → Chuột không dây (320000) và Cáp USB-C (90000).
• Dòng 2: đơn có trạng thái PAID → 5 dòng (đơn 1, 2, 5, 7, 8).
• Dòng 3: <> nghĩa là "khác" → 7 đơn không bị hủy.
Các phép so sánh: = , <> (hoặc !=), > , < , >= , <=
~~~sql
SELECT name, price FROM products WHERE price < 500000;
SELECT * FROM orders WHERE status = 'PAID';
SELECT * FROM orders WHERE status <> 'CANCELLED';
~~~

### Kết hợp điều kiện: AND, OR, IN
• AND: cả hai điều kiện đều đúng → chỉ Nguyễn Văn An.
• OR: một trong hai đúng là được → An, Châu, Dung, Lan.
• IN (...): cách viết gọn của nhiều OR → kết quả giống dòng 2.
Mẹo: khi trộn AND và OR, luôn dùng ngoặc cho rõ, ví dụ:
WHERE status = 'PAID' AND (user_id = 1 OR user_id = 3)
~~~sql
SELECT full_name FROM users WHERE city = 'Vân Thoi' AND email IS NOT NULL;
SELECT full_name, city FROM users WHERE city = 'Vân Thoi' OR city = 'Lụa Mầm';
SELECT full_name, city FROM users WHERE city IN ('Vân Thoi', 'Lụa Mầm');
~~~

### Tìm gần đúng: LIKE và BETWEEN
Giải thích:
• LIKE 'Nguyễn%': bắt đầu bằng "Nguyễn", dấu % thay cho "bất kỳ ký tự nào, bao nhiêu cũng được".
• '%@example.com': kết thúc bằng @example.com → 5 user (user 4 có email NULL nên không xuất hiện).
• Dấu _ thay cho đúng 1 ký tự, ví dụ 'A_' khớp "An".
• BETWEEN a AND b: từ a đến b, tính cả hai đầu → Bàn phím cơ (850000), Chuột không dây (320000).
~~~sql
SELECT full_name FROM users WHERE full_name LIKE 'Nguyễn%';
SELECT id, email FROM users WHERE email LIKE '%@example.com';
SELECT name, price FROM products WHERE price BETWEEN 100000 AND 1000000;
~~~

### NULL: giá trị "không biết"
• NULL không phải số 0, không phải chuỗi rỗng ''. Nó nghĩa là "không có dữ liệu".
• Dòng 1: đúng cách → trả về Phạm Thu Dung.
• Dòng 2: SAI cách → không trả về dòng nào, và cũng không báo lỗi! Đây là cái bẫy kinh điển.
• Dòng 3: những user có email → 5 dòng.
Tester nên hỏi: trường này có được phép NULL không? Màn hình hiển thị gì khi NULL?
~~~sql
SELECT id, full_name FROM users WHERE email IS NULL;
SELECT id, full_name FROM users WHERE email = NULL;
SELECT id, full_name FROM users WHERE email IS NOT NULL;
~~~

### Lỗi thường gặp
• no such column: gõ sai tên cột (fullname thay vì full_name) → xem cấu trúc bảng bằng .schema users
• near "FROM": thường do thừa dấu phẩy trước FROM, ví dụ SELECT id, full_name, FROM users
• Chuỗi phải dùng nháy đơn 'Vân Thoi'. Nháy kép "Vân Thoi" là tên cột → PostgreSQL báo lỗi; SQLite đôi khi bỏ qua, đừng dựa vào điều đó.
• Không ra kết quả dù chắc chắn có dữ liệu: kiểm tra khoảng trắng thừa, chữ hoa/thường ('paid' khác 'PAID').
~~~text
Parse error: no such column: fullname
Parse error: near "FROM": syntax error
ERROR:  column "Vân Thoi" does not exist      (PostgreSQL)
~~~

PRACTICE: Viết 3 câu SQL: (1) đơn hàng có quantity lớn hơn 1, (2) sản phẩm có stock = 0, (3) user ở Lụa Mầm có email kết thúc bằng @example.com. Ghi lại số dòng của từng câu (đáp án: 2, 1, 2).
Q: Câu nào tìm đúng các user chưa có email?
- WHERE email = NULL
+ WHERE email IS NULL
- WHERE email = ''
Q: WHERE city IN ('Vân Thoi', 'Lụa Mầm') tương đương với điều kiện nào?
- city = 'Vân Thoi' AND city = 'Lụa Mầm'
+ city = 'Vân Thoi' OR city = 'Lụa Mầm'
- city LIKE 'Vân Thoi%'
Q: Trong LIKE, ký tự % có nghĩa là gì?
+ Bất kỳ chuỗi ký tự nào, kể cả rỗng
- Đúng một ký tự
- Phần trăm

## LESSON sql-04 | Sắp xếp, giới hạn và hàm tổng hợp

### ORDER BY: sắp xếp kết quả
• ORDER BY price DESC: giá từ cao xuống thấp (DESC = giảm dần).
• ASC = tăng dần (mặc định nếu không ghi).
• Dòng 2: sắp theo city trước; cùng city thì sắp theo tên.
Kết quả mong đợi dòng 1:
Màn hình 24 inch 3500000
Tai nghe 1200000
Bàn phím cơ 850000
Chuột không dây 320000
Cáp USB-C 90000
~~~sql
SELECT name, price FROM products ORDER BY price DESC;
SELECT full_name, city FROM users ORDER BY city ASC, full_name ASC;
~~~

### LIMIT và OFFSET: lấy vài dòng đầu
• LIMIT 3: chỉ lấy 3 dòng đầu → 3 sản phẩm đắt nhất.
• LIMIT 2 OFFSET 2: bỏ qua 2 dòng đầu, lấy 2 dòng tiếp → Bàn phím cơ, Chuột không dây. Đây chính là cách làm phân trang (trang 2, mỗi trang 2 dòng).
• Với bảng hàng triệu dòng, luôn thêm LIMIT khi "xem thử" để không làm chậm database.
• SQLite, PostgreSQL, MySQL dùng LIMIT; SQL Server dùng SELECT TOP 3 ... thay thế.
~~~sql
SELECT name, price FROM products ORDER BY price DESC LIMIT 3;
SELECT name, price FROM products ORDER BY price DESC LIMIT 2 OFFSET 2;
~~~

### COUNT: đếm số dòng
• COUNT(*): đếm mọi dòng → 6.
• COUNT(email): chỉ đếm dòng có email khác NULL → 5. Khác biệt 6 và 5 chính là user thiếu email!
• Dòng 3: đếm đơn PAID → 5.
Ứng dụng: so số liệu trên màn hình báo cáo (ví dụ "Tổng đơn đã thanh toán: 5") với số đếm từ database.
~~~sql
SELECT COUNT(*) FROM users;
SELECT COUNT(email) FROM users;
SELECT COUNT(*) FROM orders WHERE status = 'PAID';
~~~

### SUM, AVG, MIN, MAX
Giải thích:
• SUM(stock): cộng tồn kho → 178.
• AVG(price): giá trung bình → 1192000.0
• MIN / MAX: nhỏ nhất / lớn nhất → 90000 và 3500000.
• AS: đặt tên dễ hiểu cho cột kết quả.
Câu lệnh có thể viết trên nhiều dòng; SQL chỉ quan tâm dấu ; ở cuối.
~~~sql
SELECT SUM(stock)  AS tong_ton_kho,
       AVG(price)  AS gia_trung_binh,
       MIN(price)  AS re_nhat,
       MAX(price)  AS dat_nhat
FROM products;
~~~

### Cột tính toán và DISTINCT
• price * stock: tạo cột mới bằng phép nhân, ví dụ Bàn phím cơ: 850000 * 20 = 17000000.
• DISTINCT: bỏ trùng lặp → 4 thành phố: Vân Thoi, Mầm Rìa, Lụa Mầm, Sợi Nếp.
Ý tưởng test: so tổng giá trị kho trên trang quản trị với SUM(price * stock) trong database.
~~~sql
SELECT name, price, stock, price * stock AS gia_tri_kho FROM products;
SELECT DISTINCT city FROM users;
~~~

### Lỗi thường gặp
• Dòng 1 trả 0 (sai!), dòng 2 trả 1 (đúng). Vì khi là chuỗi, máy so từng ký tự: '9' lớn hơn '8'.
• Bài học: cột giá mà lưu kiểu TEXT thì ORDER BY và so sánh sẽ cho kết quả lạ → báo bug thiết kế dữ liệu.
• Lỗi "misuse of aggregate: COUNT()": dùng COUNT trong WHERE → phải dùng HAVING (bài sau).
• Quên ORDER BY trước LIMIT: kết quả "3 dòng đầu" có thể khác nhau mỗi lần chạy.
~~~sql
SELECT '90000' < '850000';
SELECT 90000 < 850000;
~~~

PRACTICE: Viết câu SQL tìm 2 sản phẩm rẻ nhất còn hàng (stock > 0), và câu SQL tính tổng số lượng (SUM(quantity)) của các đơn PAID. Đáp án: Cáp USB-C, Chuột không dây; tổng = 5.
Q: COUNT(*) = 6 nhưng COUNT(email) = 5. Điều đó cho biết gì?
- Có 1 email bị trùng
+ Có 1 dòng email là NULL
- Database bị lỗi
Q: Câu nào lấy 3 sản phẩm đắt nhất?
+ ORDER BY price DESC LIMIT 3
- ORDER BY price ASC LIMIT 3
- LIMIT 3 ORDER BY price

## LESSON sql-05 | GROUP BY và HAVING: thống kê theo nhóm

### GROUP BY: chia vào từng rổ rồi đếm
Hình dung: đổ hết đơn hàng ra bàn, xếp vào từng rổ theo trạng thái, rồi đếm mỗi rổ.
Giải thích:
• GROUP BY status: gom các dòng có cùng status thành một nhóm.
• COUNT(*): đếm số dòng trong mỗi nhóm.
Kết quả mong đợi:
CANCELLED 1
PAID 5
PENDING 1
SHIPPED 1
~~~sql
SELECT status, COUNT(*) AS so_don
FROM orders
GROUP BY status
ORDER BY status;
~~~

### Đếm đơn theo từng khách hàng
Giải thích:
• Mỗi user_id thành một nhóm.
• COUNT(*): số đơn; SUM(quantity): tổng số món đã đặt.
• ORDER BY so_don DESC: ai nhiều đơn nhất lên đầu.
Kết quả mong đợi: user 1, 2, 3 mỗi người 2 đơn; user 6 và user 99 mỗi người 1 đơn.
Để ý user_id 99 — không có trong bảng users. Thống kê đã "lộ" bug dữ liệu!
~~~sql
SELECT user_id, COUNT(*) AS so_don, SUM(quantity) AS tong_so_luong
FROM orders
GROUP BY user_id
ORDER BY so_don DESC, user_id;
~~~

### HAVING: lọc sau khi gom nhóm
• WHERE lọc từng dòng TRƯỚC khi gom nhóm.
• HAVING lọc từng nhóm SAU khi gom.
• Câu trên: chỉ giữ khách có từ 2 đơn trở lên → user 1, 2, 3.
~~~sql
SELECT user_id, COUNT(*) AS so_don
FROM orders
GROUP BY user_id
HAVING COUNT(*) >= 2;
~~~

### WHERE và HAVING dùng cùng nhau
Máy làm theo thứ tự:
• Bước 1 (WHERE): chỉ giữ đơn PAID → đơn 1, 2, 5, 7, 8.
• Bước 2 (GROUP BY): gom theo user_id → user 1 có 2 đơn; user 2, 3, 99 mỗi người 1 đơn.
• Bước 3 (HAVING): giữ nhóm có từ 2 đơn → chỉ còn user 1.
Kết quả mong đợi: một dòng 1 | 2.
~~~sql
SELECT user_id, COUNT(*) AS so_don_paid
FROM orders
WHERE status = 'PAID'
GROUP BY user_id
HAVING COUNT(*) >= 2;
~~~

### Thứ tự viết một câu SELECT đầy đủ
• Đây là "khung" để ghép câu lệnh; viết sai thứ tự sẽ bị syntax error.
• Thứ tự máy thực hiện lại khác: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.
• Vì vậy tên đặt bằng AS trong SELECT thường dùng được ở ORDER BY nhưng không dùng được ở WHERE (với nhiều hệ quản trị như PostgreSQL).
~~~sql
SELECT    cột, hàm tổng hợp
FROM      bảng
WHERE     điều kiện trên từng dòng
GROUP BY  cột gom nhóm
HAVING    điều kiện trên từng nhóm
ORDER BY  cột sắp xếp
LIMIT     số dòng;
~~~

### Lỗi thường gặp
• misuse of aggregate: viết WHERE COUNT(*) >= 2 → đổi thành HAVING COUNT(*) >= 2.
• Lỗi PostgreSQL thứ hai: SELECT có cột không nằm trong GROUP BY mà cũng không nằm trong hàm tổng hợp.
• Bẫy SQLite: SQLite không báo lỗi trường hợp trên mà tự lấy một giá trị bất kỳ → kết quả trông hợp lý nhưng sai. Luôn liệt kê đủ cột trong GROUP BY.
~~~text
Parse error: misuse of aggregate: COUNT()
ERROR:  column "orders.status" must appear in the GROUP BY clause or be used in an aggregate function   (PostgreSQL)
~~~

PRACTICE: Viết câu SQL đếm số đơn theo product_id, chỉ hiển thị sản phẩm có từ 2 đơn trở lên, sắp xếp giảm dần. Đáp án: product 2 có 3 đơn, product 1 có 2 đơn.
Q: Muốn lọc các nhóm có COUNT(*) > 1, ta dùng gì?
- WHERE COUNT(*) > 1
+ HAVING COUNT(*) > 1
- ORDER BY COUNT(*) > 1
Q: Trong câu có cả WHERE và GROUP BY, WHERE được thực hiện khi nào?
+ Trước khi gom nhóm
- Sau khi gom nhóm
- Sau ORDER BY

## LESSON sql-06 | JOIN: nối các bảng lại với nhau

### Vì sao cần JOIN?
• Bảng orders chỉ lưu user_id, không lưu tên khách.
• Muốn thấy "đơn 1 của Nguyễn Văn An", ta phải nối 2 bảng qua cột chung: orders.user_id = users.id.
• JOIN giống việc ghép hai danh sách giấy bằng cách dò số thứ tự chung.
• Đơn 7 không tìm được "bạn ghép" — đó là bug ta sẽ săn ở slide sau.
~~~text
orders                         users
id | user_id | status          id | full_name
1  | 1       | PAID     --->   1  | Nguyễn Văn An
3  | 2       | SHIPPED  --->   2  | Trần Thị Bình
7  | 99      | PAID     --->   ?? (không có user 99)
~~~

### INNER JOIN: chỉ lấy dòng ghép được
Giải thích từng dòng:
• FROM orders o: lấy bảng orders, đặt biệt danh ngắn là o.
• INNER JOIN users u: nối với bảng users, biệt danh u.
• ON o.user_id = u.id: điều kiện ghép — user_id của đơn khớp với id của user.
• SELECT o.id, u.full_name: lấy cột từ cả hai bảng, ghi rõ bảng nào bằng o. và u.
Kết quả mong đợi: 7 dòng (đơn 1, 2, 3, 4, 5, 6, 8). Đơn 7 biến mất vì user 99 không tồn tại.
~~~sql
SELECT o.id AS order_id, u.full_name, o.status
FROM orders o
INNER JOIN users u ON o.user_id = u.id
ORDER BY o.id;
~~~

### Nối 3 bảng và tính thành tiền
• JOIN viết tắt cho INNER JOIN.
• Mỗi JOIN thêm một bảng và một điều kiện ON.
• thanh_tien = số lượng × đơn giá.
Kết quả mong đợi vài dòng đầu:
1 | Nguyễn Văn An | Bàn phím cơ | 1 | 850000 | 850000
2 | Nguyễn Văn An | Chuột không dây | 2 | 320000 | 640000
3 | Trần Thị Bình | Màn hình 24 inch | 1 | 3500000 | 3500000
Ý tưởng test: so thanh_tien với số tiền hiển thị trên trang chi tiết đơn hàng.
~~~sql
SELECT o.id, u.full_name, p.name AS product,
       o.quantity, p.price, o.quantity * p.price AS thanh_tien
FROM orders o
JOIN users u    ON o.user_id = u.id
JOIN products p ON o.product_id = p.id
ORDER BY o.id;
~~~

### LEFT JOIN: giữ tất cả bên trái
• LEFT JOIN: giữ MỌI dòng của bảng bên trái (users), kể cả khi không ghép được; phần bên phải khi đó là NULL.
• WHERE o.id IS NULL: chỉ giữ những user không có đơn nào.
Kết quả mong đợi: 4 Phạm Thu Dung và 5 Hoàng Gia Huy.
Ứng dụng: tìm khách chưa mua hàng, sản phẩm chưa ai đặt, user chưa được gán quyền...
~~~sql
SELECT u.id, u.full_name, o.id AS order_id
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;
~~~

### Săn bug dữ liệu bằng SQL
• Dấu -- bắt đầu một comment (ghi chú), máy bỏ qua.
• Câu 1 → an@example.com xuất hiện 2 lần.
• Câu 2 → đơn 7 (user_id 99).
• Câu 3 → đơn 8 (quantity 0 nhưng PAID).
Mỗi kết quả là một bug tiềm năng: báo kèm câu SQL để developer chạy lại được.
~~~sql
-- 1) Email bị trùng
SELECT email, COUNT(*) AS so_lan FROM users
WHERE email IS NOT NULL
GROUP BY email HAVING COUNT(*) > 1;

-- 2) Đơn hàng mồ côi (user không tồn tại)
SELECT o.* FROM orders o
LEFT JOIN users u ON o.user_id = u.id
WHERE u.id IS NULL;

-- 3) Giá trị vô lý
SELECT * FROM orders WHERE quantity <= 0;
~~~

### Lỗi thường gặp
• ambiguous column name: cả hai bảng đều có cột id → viết rõ o.id hoặc u.id.
• Ra 48 dòng: quên điều kiện ON, SQLite ghép mọi đơn với mọi user (8 × 6 = 48). Luôn kiểm tra số dòng có hợp lý không.
• PostgreSQL bắt buộc JOIN phải có ON (hoặc USING), thiếu là báo lỗi cú pháp.
• Dùng INNER JOIN khi đang tìm dòng "không ghép được" → không bao giờ thấy bug; phải dùng LEFT JOIN.
~~~text
Parse error: ambiguous column name: id
(kết quả ra 48 dòng thay vì 8)
ERROR:  syntax error at or near "ORDER"      (PostgreSQL, JOIN thiếu ON)
~~~

PRACTICE: Viết câu SQL liệt kê các sản phẩm chưa từng được đặt (dùng products LEFT JOIN orders). Sau đó viết câu SQL tính tổng thanh_tien của các đơn PAID có user hợp lệ. Đáp án: không có sản phẩm nào chưa được đặt; tổng = 2340000.
Q: Muốn tìm user chưa có đơn hàng nào, nên dùng loại JOIN nào?
- INNER JOIN
+ LEFT JOIN từ users sang orders, rồi lọc o.id IS NULL
- Không cần JOIN
Q: Lỗi "ambiguous column name: id" nghĩa là gì?
+ Cột id có ở nhiều bảng, cần ghi rõ bảng nào
- Bảng không có cột id
- id bị NULL
Q: Kết quả JOIN ra số dòng bằng tích số dòng hai bảng. Nguyên nhân hay gặp nhất?
- Database bị trùng dữ liệu
- Dùng LEFT JOIN
+ Thiếu hoặc sai điều kiện ON

### Transaction: nút "hoàn tác" trên DB test
Chạy trong sqlite3 shop.db, từng dòng:
• BEGIN: mở một giao dịch — mọi thay đổi sau đó chưa được lưu hẳn.
• UPDATE: thử đổi giá Bàn phím cơ thành 0.
• SELECT (lần 1): thấy price = 0.
• ROLLBACK: hủy mọi thay đổi từ sau BEGIN.
• SELECT (lần 2): price trở lại 850000.
Dùng COMMIT thay cho ROLLBACK nếu muốn lưu thật. Transaction là lưới an toàn trên DB test, không phải giấy phép để sửa PROD.

BEGIN;
UPDATE products SET price = 0 WHERE id = 1;
SELECT id, name, price FROM products WHERE id = 1;
ROLLBACK;
SELECT id, name, price FROM products WHERE id = 1;
~~~

• relation does not exist: kết nối nhầm database/schema, hoặc tên bảng phân biệt hoa thường.
• cannot start a transaction within a transaction: đã có BEGIN đang mở (hoặc công cụ giao diện tự mở sẵn) → chạy ROLLBACK, hoặc dùng sqlite3 dòng lệnh.
~~~text

ERROR:  relation "orders" does not exist
Runtime error: cannot start a transaction within a transaction
~~~

## LESSON sql-08 | Subquery và CTE để chia bài toán

### Chia phép đối soát thành bước có tên
Kho giả định Gió Mầm cần biết số tiền từng khách đã trả. CTE dưới chỉ gom payment thành công thành một dòng mỗi khách rồi nối customers; nó làm rõ hạt dữ liệu, không hứa luôn tăng tốc.
~~~sql
WITH paid AS (
 SELECT customer_id,SUM(amount) AS total
 FROM payments WHERE status='paid' GROUP BY customer_id
) SELECT c.id,COALESCE(p.total,0) AS total
FROM customers c LEFT JOIN paid p ON p.customer_id=c.id;
~~~

### Truy vấn tồn tại phải liên hệ đúng khóa
Tìm khách chưa có đơn bằng NOT EXISTS. Điều kiện o.customer_id=c.id biến câu hỏi thành kiểm cho từng khách; bỏ nó sẽ hỏi cả bảng có bất kỳ đơn nào hay không.
~~~sql
SELECT c.id FROM customers c
WHERE NOT EXISTS (
 SELECT 1 FROM orders o WHERE o.customer_id=c.id
);
~~~

### NULL có thể làm NOT IN khác dự đoán
Nếu tập bị loại chứa NULL, phép NOT IN có thể trả unknown. Fixture nhỏ cho thấy vì sao không đổi NOT EXISTS sang NOT IN một cách máy móc.
~~~sql
CREATE TEMP TABLE blocked(customer_id INTEGER);
INSERT INTO blocked VALUES(NULL),(2);
SELECT 1 NOT IN (SELECT customer_id FROM blocked);
SELECT NOT EXISTS(SELECT 1 FROM blocked WHERE customer_id=1);
~~~

### Expected viết tay trước khi chạy
Tạo ba khách: có hai payment paid, chưa có payment, chỉ có payment failed. Tính tổng bằng tay, rồi kiểm từng dòng để phát hiện lọc trạng thái sai hoặc nhân tổng do join.

### Tối ưu sau khi hiểu kết quả
Giữ alias rõ nghĩa và kiểm grain trước. Muốn nói CTE nhanh hơn cần kế hoạch và số đo với dữ liệu đại diện; cách viết dễ đọc không thay thế index hay đo thực nghiệm.

PRACTICE: Tạo fixture SQLite cho ba khách và các payment tự đặt. Viết CTE tổng tiền và NOT EXISTS khách chưa có đơn; thêm NULL, so NOT IN và nộp expected/actual giải thích từng khác biệt.
Q: CTE chủ yếu giúp gì trong bài?
+ Đặt tên bước trung gian
- Luôn tăng tốc
- Tạo index vĩnh viễn
Q: Tìm khách chưa từng có đơn thường dùng gì?
+ NOT EXISTS có liên hệ đúng khóa
- NOT IN bất kể NULL
- JOIN thiếu ON

## LESSON sql-09 | Hàm cửa sổ và chọn bản ghi mới nhất

### Lấy một sự kiện mới nhất mỗi đơn
Nhật ký giả định có nhiều trạng thái cho cùng order_id. Chia theo đơn và xếp giờ giảm dần; event_id là khóa phân xử khi giờ bằng nhau, để dòng rn=1 có ý nghĩa xác định.
~~~sql
WITH ranked AS (
 SELECT *,ROW_NUMBER() OVER (
 PARTITION BY order_id ORDER BY created_at DESC,event_id DESC
 ) AS rn FROM order_events
) SELECT order_id,status FROM ranked WHERE rn=1;
~~~

### Đối chiếu số dư với dòng liền trước
LAG nhìn giá trị trước trong cùng tài khoản. Dòng đầu trả NULL vì chưa có lịch sử, không phải thay đổi bằng không; báo cáo phải giữ sự khác biệt này.
~~~sql
SELECT account_id,event_id,balance,
 LAG(balance) OVER(PARTITION BY account_id ORDER BY event_id) AS previous
FROM balance_events;
~~~

### Frame tường minh cho cộng dồn
Khi muốn cộng lần lượt từng dòng, chỉ rõ ROWS và thứ tự duy nhất. Nếu để peer group theo timestamp trùng, một số frame có thể cho kết quả khác cộng từng sự kiện.
~~~sql
SELECT account_id,event_id,amount,
 SUM(amount) OVER(PARTITION BY account_id ORDER BY event_id
 ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total
FROM ledger;
~~~

### Không lẫn cửa sổ với gom nhóm
GROUP BY rút nhiều dòng thành một nhóm. Window giữ chi tiết và bổ sung giá trị tính; lọc rn ở lớp truy vấn ngoài vì alias cửa sổ chưa phải điều kiện WHERE cùng lớp.

### Bộ thử cố ý có thời điểm bằng nhau
Tạo đơn chỉ có một sự kiện và đơn có hai timestamp giống nhau. Đổi thứ tự INSERT rồi kiểm bản ghi mới nhất và tổng chạy vẫn theo khóa đã định, không dựa vào thứ tự lưu.

PRACTICE: Viết ba query latest-state, previous-balance, running-total. Bàn giao fixture và bảng kết quả từng dòng; giải thích tie-break, NULL đầu phân vùng và lý do dùng lớp CTE để lọc rn.
Q: ROW_NUMBER chọn mới nhất khi giờ trùng cần gì?
+ Khóa phân xử duy nhất
- Chỉ ORDER BY timestamp
- Lấy ngẫu nhiên một dòng
Q: Window function khác GROUP BY ra sao?
+ Thường giữ chi tiết từng dòng
- Luôn chỉ còn một dòng
- Luôn bỏ NULL

## LESSON sql-10 | Transaction, khóa và bất biến nghiệp vụ

### Gom hai thay đổi ví trong một transaction
Ví điểm lab chuyển 20 điểm từ W1 sang W2. Ví dụ có hai UPDATE nhưng ứng dụng bắt buộc kiểm mỗi bước ảnh hưởng đúng một dòng; nếu không thì ROLLBACK thay vì COMMIT phần đã làm.
~~~sql
BEGIN;
UPDATE wallets SET balance=balance-20 WHERE id='W1' AND balance>=20;
-- Ứng dụng xác nhận đúng 1 dòng, nếu không: ROLLBACK.
UPDATE wallets SET balance=balance+20 WHERE id='W2';
-- Xác nhận W2 tồn tại trước khi commit.
COMMIT;
~~~

### Constraint bảo vệ từng dòng
CHECK ngăn số dư âm ở bảng SQLite lab. Nó chưa đủ kiểm tổng điểm hai ví hay người nhận đúng, nên phải kết hợp với transaction và quy tắc nghiệp vụ.
~~~sql
CREATE TABLE wallets(
 id TEXT PRIMARY KEY,
 balance INTEGER NOT NULL CHECK(balance>=0)
);
INSERT INTO wallets VALUES('W1',50),('W2',10);
~~~

### Quan sát khóa bằng hai connection
BEGIN IMMEDIATE trong SQLite lấy quyền ghi sớm và có thể gặp busy nếu đã có phiên ghi. Hành vi cụ thể này không đại diện mọi hệ quản trị; ghi timeout và chính sách retry có giới hạn.
~~~sql
-- Phiên A trên file lab:
BEGIN IMMEDIATE;
UPDATE wallets SET balance=balance-5 WHERE id='W1';
-- Thử phiên B trong lúc A chưa kết thúc.
-- Sau khi quan sát ở B, kết thúc A:
ROLLBACK;
~~~

### Tránh ghi đè từ giá trị đã đọc cũ
Hai tiến trình cùng đọc số dư rồi ghi số tính sẵn có thể làm mất cập nhật. Dùng cập nhật tương đối với điều kiện và kiểm affected rows; không giữ transaction mở trong lúc chờ người dùng.

### Bất biến sau lỗi giữa chừng
Gây lỗi ở bước cộng người nhận và rollback. So cả từng ví lẫn tổng trước/sau; thêm thiếu điểm, ví không có và hai yêu cầu tranh cùng số dư để kiểm ranh giới.

PRACTICE: Chạy hai phiên SQLite, ghi bảng thao tác xen kẽ và kết quả busy. Test lỗi giữa hai UPDATE phải khôi phục số dư ban đầu; mọi thao tác chỉ trong tệp ví giả định.
Q: Transaction chuyển điểm cần bất biến nào?
+ Hai vế cùng commit hoặc rollback
- Chỉ trừ thành công
- Tự đổi mọi NULL thành 0
Q: Đọc số dư rồi ghi giá trị tính sẵn có rủi ro gì?
+ Mất cập nhật khi cạnh tranh
- Không thể sai trong transaction
- SQL tự sửa quy tắc

## LESSON sql-11 | Index, EXPLAIN và đo truy vấn

### Bắt đầu từ mẫu truy vấn thực sự dùng

EXPLAIN QUERY PLAN

CREATE INDEX ix_orders_customer_date

SELECT id,total FROM orders

SELECT id FROM orders

### Đọc plan cùng độ chọn lọc

### Kiểm tác động lên đường ghi
Đo thêm nhập lô và dung lượng file. Giữ hoặc bỏ index dựa trên câu hỏi sản phẩm và ngân sách, chỉ thử xóa index ở bản sao lab để không ảnh hưởng dữ liệu đang dùng.

## LESSON sql-12 | Migration và đối soát dữ liệu trước sau

### Chuyển schema cần giữ nghĩa dữ liệu cũ
Lab thêm currency cho orders. Giả định toàn bộ đơn cũ cùng đơn vị tiền giả DLM phải được ghi rõ; không tự áp mặc định cho một hệ thống có nhiều loại tiền chưa được xác nhận.
~~~sql
ALTER TABLE orders ADD COLUMN currency TEXT;
UPDATE orders SET currency='DLM' WHERE currency IS NULL;
SELECT COUNT(*) FROM orders WHERE currency IS NULL;
~~~

### Chụp nhiều bất biến theo nhóm
Đếm dòng, khóa khác nhau và tổng tiền theo trạng thái. Dùng đơn vị nhỏ dạng số nguyên để tránh sai số thập phân trong phép đối soát tiền lab.
~~~sql
SELECT status,COUNT(*) AS n,COUNT(DISTINCT id) AS ids,
 SUM(total_minor) AS money
FROM orders GROUP BY status ORDER BY status;
~~~

### Tìm bản ghi mất, dư và đổi giá trị
Hai bản sao before/after giúp chỉ ra id lệch. EXCEPT trên id chưa so nội dung, nên cần truy vấn nối theo khóa để phát hiện tiền bị sửa dù số dòng khớp.
~~~sql
SELECT id FROM orders_before EXCEPT SELECT id FROM orders_after;
SELECT id FROM orders_after EXCEPT SELECT id FROM orders_before;
SELECT b.id FROM orders_before b JOIN orders_after a ON a.id=b.id
WHERE b.total_minor<>a.total_minor;
~~~

### Quay lui phải tính cả giao dịch mới
Rollback cấu trúc không tự khôi phục thông tin đã bỏ. Xác định snapshot, điểm dừng ghi và cách xử lý dữ liệu phát sinh; bài lab cố định dữ liệu để tập trước khi bàn tình huống có ghi đồng thời.

### Lần chạy thứ hai cần kết quả đã định
Không mặc định mọi migration idempotent. Ghi version và checksum, quy định chạy lại báo đã áp dụng hoặc không đổi gì; không catch toàn bộ lỗi rồi ghi thành công giả.

PRACTICE: Migration currency trên bản sao, đối soát theo trạng thái và truy id lệch. Cố ý mất một dòng và thêm một dòng để COUNT vẫn bằng nhau; phục hồi snapshot và xác nhận bất biến.
Q: Thêm trường bắt buộc vào dữ liệu cũ cần gì?
+ Chính sách backfill và xác nhận
- Chỉ sửa schema
- Xóa NULL không báo
Q: COUNT trước/sau migration bằng nhau có đủ không?
+ Không, còn khóa và tổng theo nhóm
- Có, chắc dữ liệu giống nhau
- Chỉ xem thêm một dòng

## LESSON sql-13 | Dự án: kiểm sổ đơn và thanh toán giả

### Chốt hạt dữ liệu sổ đơn
Quán giả định Vệt Bông có một đơn và nhiều lần thanh toán. Mỗi đơn chỉ tính tổng một lần; payment failed không đóng góp doanh thu. Nêu chính sách thanh toán một phần trước khi kết luận thiếu tiền là lỗi.
~~~text
orders: id,customer_id,total_minor,status
payments: id,order_id,amount_minor,status
Bất biến lab: đơn paid có paid_sum = total_minor
Ngoại lệ: thiếu tiền, dư tiền, payment mồ côi
~~~

### Gom payment trước khi join
Nếu cộng order_total sau join một-nhiều sẽ nhân tiền đơn. CTE gom theo order_id rồi nối, dùng COALESCE riêng ở phép tính cần coi chưa có payment là không đồng.
~~~sql
WITH p AS (
 SELECT order_id,SUM(amount_minor) AS paid_sum
 FROM payments WHERE status='paid' GROUP BY order_id
) SELECT o.id,o.total_minor,COALESCE(p.paid_sum,0) AS paid_sum
FROM orders o LEFT JOIN p ON p.order_id=o.id
WHERE o.status='paid' AND COALESCE(p.paid_sum,0)<>o.total_minor;
~~~

### Kiểm ràng buộc và payment không có đơn
SQLite cần bật foreign_keys theo connection. Dữ liệu thô có thể nằm bảng staging không constraint để phát hiện lỗi trước chuyển bảng sạch; không tắt ràng buộc trong kho đang dùng để nạp bừa.
~~~sql
PRAGMA foreign_keys=ON;
SELECT p.id FROM payments p LEFT JOIN orders o ON o.id=p.order_id
WHERE o.id IS NULL;
PRAGMA foreign_key_check;
~~~

### Fixture có sai khác để kiểm độ nhạy
Tạo sáu nhóm: chưa trả, đúng tiền, thiếu, dư, hai paid và mồ côi. Expected ghi từng id với lý do, kể cả ca không lỗi; query rỗng trên toàn dữ liệu tốt chưa chứng minh kiểm đúng.

### Bàn giao quyết định có giới hạn
Tách lỗi dữ liệu đã chứng minh khỏi câu hỏi cần xác nhận nghiệp vụ. Nộp script dựng lab, query đọc, expected, kế hoạch index và phục hồi; script xóa hoặc sửa dữ liệu không tự chạy khi mở tài liệu.

PRACTICE: Nộp lab SQLite với sáu nhóm fixture và tám phép kiểm, trong đó có đối soát số lượng, tiền, khóa và latest-state. Đo một query, thử migration, phục hồi và viết báo cáo id lỗi kèm ảnh hưởng.
