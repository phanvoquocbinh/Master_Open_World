## LESSON mobile-dev-02 | Dart: kiểu, null safety và async

### Kiểu rõ giúp giảm giả định ẩn
Dart phân biệt nullable, final cho binding không gán lại và const cho giá trị compile-time theo quy tắc ngôn ngữ. Null safety không kiểm dữ liệu ngoài hay quyền; tránh dùng dynamic/! để bỏ qua mọi lỗi.

### Parser model kiểm runtime
Đây là lib/classes/class_info.dart độc lập. Map từ JSON phải có id string không rỗng và remaining int không âm; tạo object mới để không giữ field không thuộc DTO. Quy tắc qty/quota server vẫn riêng.
~~~text
class ClassInfo {
 final String id; final int remaining;
 const ClassInfo(this.id,this.remaining);
 factory ClassInfo.parse(Object? raw){
  if(raw is! Map<String,dynamic>)throw const FormatException('shape');
  final id=raw['id'];final n=raw['remaining'];
  if(id is! String || id.isEmpty || n is! int || n<0)throw const FormatException('class');
  return ClassInfo(id,n);
 }
}
~~~

### Future không làm UI được phép dùng context mãi
Hàm dưới minh họa await và lỗi, không phát request. Catch xử lý theo error contract ở tầng app; timeout trên Future không tự ngừng công việc gốc nên cần thiết kế cancellation riêng khi có mạng.
~~~text
Future<int> delayedCount() async {
 await Future<void>.delayed(const Duration(milliseconds:20));
 return 2;
}
Future<void> demo() async {
 final count=await delayedCount().timeout(const Duration(seconds:1));
 assert(count==2);
}
~~~

### Ca null và kiểu sai phải được ghi
Không ép remaining.toString rồi parse để âm thầm nhận mọi kiểu. Chốt khác biệt missing/null/chuỗi số theo contract; exception FormatException chỉ báo dữ liệu không hợp lệ, không nên chứa toàn raw body.
~~~text
valid: {id:CL7,remaining:1}
invalid: null hoặc list thay object
invalid: id rỗng, remaining=-1
invalid: remaining="1" hoặc true
nullable field tương lai: nêu rõ missing/null nghĩa gì
UI không hiển thị stacktrace cho người học
~~~

### Collection có tác dụng phụ cần thấy được
final List vẫn có thể thay nội dung; muốn snapshot không cho sửa dùng List.unmodifiable với kiểu phù hợp. Không giữ reference list mutable rồi cho rằng viewmodel có immutable state vì biến khai báo final.

PRACTICE: Viết unit test parser cho10ca, thêm field note nullable với policy missing/null rõ. Nộp ví dụ final list vẫn sửa được và snapshot unmodifiable, không dùng ! để che lỗi.
Q: Dart null safety làm gì?
+ Phân biệt kiểu nullable ở thời điểm kiểm kiểu, không thay validate dữ liệu ngoài
- Làm mọi API không lỗi
- Cho dùng ! ở mọi nơi
Q: Future.timeout có tự hủy toàn bộ tác vụ gốc không?
+ Không
- Có luôn
- Có nếu catch TimeoutException

## LESSON mobile-dev-03 | Widget và vòng đời hiển thị

### Widget mô tả cấu hình, State giữ vòng đời
StatelessWidget xây UI từ input, StatefulWidget tạo State khi cần trạng thái sống theo element. Không lưu business state bền chỉ trong widget nếu yêu cầu phục hồi sau restart; key giúp identity theo contract.

### StatefulWidget có tài nguyên được dispose
Đây là file widget đầy đủ với controller. Build không gọi request hay tạo controller mới. State sở hữu controller và giải phóng trong dispose; nếu controller được truyền từ ngoài thì ownership phải đổi rõ.
~~~text
import 'package:flutter/material.dart';
class NoteBox extends StatefulWidget {
 const NoteBox({super.key});
 @override State<NoteBox> createState()=>_NoteBoxState();
}
class _NoteBoxState extends State<NoteBox> {
 final controller=TextEditingController();
 @override void dispose(){controller.dispose();super.dispose();}
 @override Widget build(BuildContext context)=>TextField(
  controller:controller,decoration:const InputDecoration(labelText:'Ghi chú lớp'),
 );
}
~~~

### Async gap phải kiểm đúng mounted
Đoạn callback đặt trong build với context đang dùng. Kiểm sau await và trước Navigator; nếu dữ liệu trả về cần setState thì State cũng phải còn mounted. Generation guard ở bài API giải quyết thêm response cũ, khác mounted.
~~~text
onPressed:() async {
 await Future<void>.delayed(const Duration(milliseconds:50));
 if(!context.mounted)return;
 Navigator.of(context).pop();
}
~~~

### Vẽ lifecycle để tìm leak
initState chạy khi State được tạo, didUpdateWidget khi cấu hình tương ứng đổi, dispose khi State kết thúc. Listener/subscription cần đăng ký và hủy theo ownership; giữ context trong service lâu dài là dấu hiệu nên review.
~~~text
createState -> initState -> build (có thể nhiều lần)
parent đổi input -> didUpdateWidget -> build
remove element -> dispose
controller/listener/timer do State sở hữu -> cleanup
network hoàn tất sau dispose -> không setState/context access
~~~

### Key là định danh UI, không phải auth
Key ổn định giúp list item giữ đúng State khi reorder. Không dùng index làm key nếu item có identity thay đổi vị trí; key cũng không xác thực dữ liệu hay quyết định user được xem item.

PRACTICE: Tạo list NoteBox có key theo id giả, test reorder không chuyển ghi chú sang lớp khác. Thêm callback async rồi rời màn hình, chứng minh không cập nhật State đã dispose.
Q: build nên chứa gì?
+ Mô tả UI từ state hiện tại, tránh side effect lặp
- Tạo request mới mọi lần
- Ghi DB mỗi lần
Q: Sau await dùng context cần gì?
+ Kiểm mounted của context liên quan nếu có async gap
- Chỉ await đủ lâu
- Luôn dùng context cũ

## LESSON mobile-dev-05 | State và luồng dữ liệu

### State rõ thay nhiều bool tự do
Ví dụ danh sách lớp có loading/data/error. Khi refresh giữ data cũ hay ẩn phải do UX contract quyết định; đừng để isLoading=false,error!=null,success=true cùng tồn tại không có nghĩa.

### Model trạng thái có kiểu
Dart sealed classes giúp biểu diễn tập trạng thái đóng trong library. Bản mẫu cho một tải đơn; refresh có data cũ hoặc pagination sẽ cần mở model, không ép mọi tính năng vào ba field bool.
~~~text
sealed class ClassesState {const ClassesState();}
class ClassesLoading extends ClassesState {const ClassesLoading();}
class ClassesData extends ClassesState {
 final List<ClassInfo> items;
 ClassesData(Iterable<ClassInfo> xs):items=List.unmodifiable(xs);
}
class ClassesError extends ClassesState {
 final String code;const ClassesError(this.code);
}
~~~

### Repository giả giữ test không phụ thuộc mạng
Abstraction này nhập ClassInfo từ file model. ViewModel nhận repository qua constructor, UI quan sát state bằng cơ chế được chọn; ChangeNotifier là một lựa chọn đơn giản, không là yêu cầu mọi app phải dùng.
~~~text
abstract interface class ClassRepository {
 Future<List<ClassInfo>> list();
}
class FakeClasses implements ClassRepository {
 @override Future<List<ClassInfo>> list() async=>[const ClassInfo('CL7',1)];
}
~~~

### Luồng dữ liệu và ownership phải đọc được
UI phát intent, ViewModel điều phối và đổi state, repository lấy/ghi dữ liệu theo contract. Server chốt quyền/quota. Ai tạo notifier/client thì có trách nhiệm dispose theo thiết kế, tránh nhiều màn hình đóng chung client đang dùng.
~~~text
user refresh -> ViewModel.load
 -> repository.list -> DTO/domain validation
 -> state Data hoặc Error code
 -> UI render + semantics
submit -> server kiểm quyền/quota/idempotency
UI disable button chỉ giảm bấm lặp, không là control cuối
~~~

### Derived state không lưu lặp tùy tiện
Nếu số lớp còn chỗ tính được từ list hiện tại, cân nhắc getter thay biến đếm phải đồng bộ thủ công. Mỗi nguồn state thêm vào tạo khả năng lệch, nên chỉ cache khi có lý do và invalidation rõ.

PRACTICE: Nộp state diagram tải/refresh/error, fake repository và một viewmodel không biết BuildContext. Test transition và snapshot list không bị caller sửa; ghi ai sở hữu notifier/client.
Q: State loading/error/data nên thiết kế ra sao?
+ Có trạng thái và chuyển tiếp rõ, tránh tổ hợp bool mâu thuẫn
- Năm bool tự do không contract
- Luôn chỉ có loading
Q: ViewModel có nên quyết định quyền quota cuối không?
+ Không, server vẫn authoritative
- Có vì UI đã khóa nút
- Có nếu typed

## LESSON mobile-dev-06 | Form và validate có trợ năng

### Form giúp người dùng sửa đúng chỗ
Dùng label rõ, lỗi cụ thể và không chỉ đổi màu. Trim/normalize phải theo ý nghĩa field, không sửa dữ liệu bí mật tùy tiện; form lab chỉ nhập ghi chú, không nhập mật khẩu thật.

### Validate đồng bộ trên field
Ví dụ đặt trong State có formKey GlobalKey<FormState>, note controller được dispose như bài3. Length ở đây là code unit của Dart string, không hứa là số grapheme hiển thị; nếu sản phẩm yêu cầu khác cần thư viện/rule phù hợp.
~~~text
final formKey=GlobalKey<FormState>();
// Trong build, note là TextEditingController do State sở hữu.
Form(key:formKey,child:TextFormField(
 controller:note,
 decoration:const InputDecoration(labelText:'Ghi chú đăng ký'),
 validator:(v){
  if(v==null || v.trim().isEmpty)return 'Nhập ghi chú cho lớp';
  if(v.length>120)return 'Ghi chú vượt giới hạn120đơn vị UTF-16';
  return null;
 },
));
~~~

### Submit cần chống nhiều lệnh cục bộ
Đoạn là pseudocode điều phối, không phải widget Dart hoàn chỉnh: cần state flag, viewmodel và error map được cài. Disabled button giảm bấm lặp, còn idempotency/quota do server quyết định; form valid chưa nghĩa đăng ký thành công.
~~~text
on submit:
 if submitting: return
 if form.validate()==false: focus lỗi đầu, return
 submitting=true
 await viewmodel.submit(validated values)
 if still mounted: render result/focus/error theo state
 finally: reset flag theo ownership, không setState sau dispose
~~~

### Kiểm semantics cùng thông điệp lỗi
Test lỗi bằng screen reader/keyboard theo target, nhãn không bị duplicate và focus có thứ tự hợp lý. Không đặt Semantics wrapper tùy tiện làm đọc hai lần; dùng widget có semantics chuẩn trước, kiểm thực tế rồi bổ sung.
~~~text
Cases: rỗng, toàn space, dài quá, tiếng Việt, paste
server validation: field error map về đúng trường
network fail: giữ draft và cho thử lại có chủ đích
accessibility: label,error,focus không chỉ màu
privacy: toast/log không chứa raw note nếu có dữ liệu riêng
~~~

### Server error không phải lỗi mạng chung
HTTP400field,403quyền,409hết chỗ và timeout có nghĩa khác. Map code ổn định sang Việt dễ hiểu, giữ nội dung form khi phù hợp, không tự retry command có tác dụng phụ mà không có protocol.

PRACTICE: Viết form ghi chú và test validation/submit đôi/server field error; kiểm nhãn/focus với công cụ target. Nộp policy length và case tiếng Việt tổ hợp, không gọi length là số chữ người nhìn.
Q: Form client validate có thay server validate không?
+ Không
- Có nếu regex dài
- Có nếu app ký release
Q: Thông báo lỗi form cần gì cho trợ năng?
+ Nhãn, nội dung cụ thể, focus/semantics phù hợp
- Chỉ đổi màu đỏ

## LESSON mobile-dev-07 | Gọi API, hủy và báo lỗi

### Mạng có nhiều lớp lỗi riêng
API lab chỉ localhost trên máy học viên. Trên emulator/device, localhost có thể là thiết bị chứ không là máy host: dùng reverse/tunnel cục bộ được cấu hình và ghi base URL tương ứng, không đổi sang API công cộng để tiện.

### Inject client và parse có kiểm
Dart snippet dùng package:http mã nguồn mở đã khai báo dependency trong project lab, import dart:convert và model. Timeout không tự hủy underlying request; repo không đóng client do caller sở hữu. Quyền INTERNET/transport policy theo target phải cấu hình trong lab.
~~~text
import 'dart:convert';
import 'package:http/http.dart' as http;
Future<ClassInfo> fetchClass(http.Client client,Uri uri) async {
 final r=await client.get(uri).timeout(const Duration(seconds:3));
 if(r.statusCode!=200)throw StateError('HTTP_${r.statusCode}');
 final Object? raw=jsonDecode(r.body);
 return ClassInfo.parse(raw);
}
~~~

### Generation guard chặn dữ liệu cũ đè mới
Pseudocode cho ViewModel: mỗi lần load có generation riêng; khi dispose tăng generation/đánh dấu closed. Guard bảo vệ state, còn cancel request nếu client hỗ trợ cần ownership rõ và xử lý riêng, không gọi close client dùng chung để hủy một request.
~~~text
load:
 mine=++generation; emit loading
 try result=await repository.list()
 if closed or mine!=generation: bỏ kết quả
 else emit data
 catch error: cũng kiểm closed/generation trước emit
dispose: closed=true;generation++;cleanup tài nguyên sở hữu
~~~

### Fake response tạo race tái hiện được
Test không sleep đoán thời gian, dùng Completer/fake để điều khiển thứ tự. Kiểm cả late success và late error, không chỉ một case data; command timeout cần trạng thái unknown/reconcile thay vì khẳng định chưa ghi.
~~~text
A request bắt đầu -> B request bắt đầu
B hoàn tất dataB -> UI hiển thị B
A hoàn tất dataA -> UI vẫn B
A late error -> không đè thành error
dispose trước hoàn tất -> không notify/setState
HTTP200 badJSON/sai schema -> lỗi dữ liệu, không data thành công
~~~

### Cancellation không hoàn tác side effect server
Đóng kết nối hoặc rời màn hình không chứng minh server chưa nhận lệnh. Gửi đăng ký cần idempotency key và tra trạng thái theo contract; parse/network/auth lỗi không gom hết thành một thông báo sai nghĩa.

PRACTICE: Nộp repository có inject client và test status/JSON/schema/timeout, một race A/B điều khiển bằng fake. Ghi base URL cho target lab và phân biệt bỏ response cũ, hủy request, hủy nghiệp vụ.
Q: Response HTTP200 có đủ coi dữ liệu hợp lệ không?
+ Không, còn JSON/schema/miền và context
- Có luôn
- Có nếu mạng nhanh
Q: Bỏ qua response cũ có đồng nghĩa đã hủy request không?
+ Không
- Có luôn

## LESSON mobile-dev-08 | Routing và lưu trạng thái điều hướng

### Điều hướng là trạng thái cần thiết kế
Lab có danh sách, chi tiết lớp và phiếu của học viên. Chốt system back, deep link, form chưa lưu và trạng thái hết phiên. App nhỏ có thể dùng Navigator, app có URL/deep link phức tạp xem Router hoặc package mã nguồn mở phù hợp.

### Push route có tham số rõ
Đoạn nằm trong callback của page, nhập material.dart và ClassPage từ file tương ứng. classId là dữ liệu đã validate, page tự tải qua repository; không truyền cả model mutable hoặc secret vào route như nguồn đáng tin vĩnh viễn.
~~~text
await Navigator.of(context).push<void>(
 MaterialPageRoute(builder:(_)=>ClassPage(classId:'CL7')),
);
if(!context.mounted)return;
// Nếu cần refresh khi quay lại, gọi intent có ownership rõ.
~~~

### Deep link không bỏ qua quyền
Parse route path thành id theo allowlist, hiển thị loading/auth-required/not-found theo contract và để server kiểm tài nguyên. URL không chứa session token, email hay note riêng; không gọi mọi query param là config đáng tin.
~~~text
incoming path: /classes/CL7
parse: pattern/id giới hạn -> route state
auth: phiên hết -> luồng login giữ đích an toàn
load: repository + server authorization
response: data/not_available theo contract
back: quay lại danh sách, không tạo vòng login
~~~

### Restoration khác cache nghiệp vụ
Khôi phục route/scroll/draft có chính sách riêng, không coi dữ liệu cũ là xác nhận đăng ký mới. Nếu user logout, state riêng của user trước phải bị xóa/không rò sang user sau; kiểm process death theo target.
~~~text
Navigation cases:
 list -> detail -> back giữ scroll theo UX
 deep link cold start -> đúng màn/đúng auth
 expired session -> login -> quay lại đích hợp lệ
 logout S7/login S8 -> không còn phiếu S7
 draft unsaved -> confirm rời hoặc autosave theo policy
~~~

### Không thêm back button trùng native tùy tiện
Thứ tự màn, hệ thống back và browser history nếu web cần kiểm cùng nhau. Modal và nested navigator có scope riêng; ghi rõ pop đang đóng dialog hay page để tránh mất dữ liệu ngoài ý muốn.

PRACTICE: Nộp route map, deep-link parser và ma trận back/cold start/logout/draft. Kiểm server vẫn chặn phiếu khác chủ dù route biết id; ghi case đã chạy theo target thực tế.
Q: Routing cần chốt gì ngoài màn hình đích?
+ Back/deep link/state restoration/quyền và dữ liệu chưa lưu
- Chỉ tên route
- Chỉ animation
Q: Biết route /receipt/R7 có thay quyền xem không?
+ Không
- Có nếu app không có nút
- Có nếu id khó đoán

## LESSON mobile-dev-09 | Lưu cục bộ và đồng bộ ngoại tuyến

### Cache đọc và queue ghi là hai việc khác
Cache giúp mở danh sách khi mạng yếu, phải có timestamp/version và nhãn dữ liệu cũ. Ghi đăng ký offline cần pending/failed/confirmed rõ, không giảm quota chính thức trên client rồi báo thành công chắc chắn.

### Outbox cục bộ giữ ý định ổn định
JSON là model lưu giả cho một lệnh, không chứa credential. Intent id/idempotency key được tạo một lần khi người dùng xác nhận, giữ qua retry; server phải thực thi contract chống lặp theo actor/key và payload.
~~~json
{"intentId":"LAB-I7","kind":"register","classId":"CL7","qty":1,"idempotencyKey":"LAB-KEY-I7-NOT-SECRET","state":"pending","attempts":0}
~~~

### Reconcile khi timeout không biết đã ghi chưa
Pseudocode cần storage transaction khi chuyển state, dedupe và chính sách khôi phục sau crash. Thử lại có backoff/budget, không retry mọi lỗi401/403/validation; server hết chỗ phải là kết quả rõ để người dùng xử lý.
~~~text
pending -> sending -> confirmed(response chắc chắn)
sending -> timeout/unknown -> tra trạng thái theo key/contract
unknown -> retry cùng key nếu policy cho phép
validation/forbidden -> failed không retry mù
app crash -> đọc outbox và reconcile, không tự sinh key mới
server conflict -> UI thông báo, không ghi đè ý định khác
~~~

### Dữ liệu cục bộ cũng cần riêng tư
Giữ tối thiểu, xóa theo logout/retention và phân vùng theo user. Preferences không là nơi lưu password/server secret. Secure storage có bảo đảm theo nền tảng và threat model riêng; mã hóa không thay quyền truy cập hoặc lifecycle.
~~~text
Storage policy lab:
 cache catalogue: public giả, TTL/version rõ
 draft note: theo actor, xóa khi logout nếu policy yêu cầu
 outbox: actor/key/state, không raw token
 credentials: cơ chế platform phù hợp nếu thực sự cần
 migrations: version+atomic update, test app nâng cấp
~~~

### Conflict là quyết định sản phẩm
Hai thiết bị sửa ghi chú hoặc đăng ký cùng lớp có thể tranh state. Last-write-wins không luôn đúng; dùng version/error và lựa chọn hợp nhất khi cần, không che conflict bằng toast chung đã đồng bộ.

PRACTICE: Tạo fake outbox có hai lệnh, mô phỏng crash sau server commit trước nhận response. Nộp state timeline, key giữ ổn định và UI unknown/confirmed; test logout không lộ draft người trước.
Q: Offline queue cho lệnh ghi cần gì?
+ Trạng thái pending, idempotency và conflict/retry policy
- Gửi lại vô hạn
- Báo confirmed ngay
Q: Local storage có nên giữ mật khẩu plaintext không?
+ Không
- Có nếu app private
- Có nếu JSON nhỏ

## LESSON mobile-dev-10 | Quyền, nền và vòng đời app

### Xin quyền theo việc người dùng đang làm
App đặt lớp cơ bản không cần danh bạ/vị trí liên tục. Chỉ khi thêm tính năng có lý do mới xin quyền tối thiểu, giải thích mục đích và cho phép dùng phần không liên quan khi người dùng từ chối.

### AppLifecycleListener giúp quan sát resume
Đây là fragment trong State, cần import material.dart và field listener; init/dispose sở hữu listener. Callback chỉ phát intent refresh có guard, không khẳng định app chạy liên tục lúc background hay server chưa thay đổi.
~~~text
late final AppLifecycleListener lifecycle;
@override void initState(){
 super.initState();
 lifecycle=AppLifecycleListener(onResume:(){
  // Gọi viewmodel.refresh có generation/closed guard đã cài.
 });
}
@override void dispose(){lifecycle.dispose();super.dispose();}
~~~

### Background task không là timer vô hạn
OS có thể suspend hoặc kill process. Chọn API/plugin được duy trì hỗ trợ target và tuân giới hạn platform, giữ task idempotent và có deadline; không dùng timer.periodic như cam kết đồng bộ kể cả app đóng.
~~~text
foreground -> user thấy state trực tiếp
inactive/paused -> có thể không còn được chạy
resume -> revalidate phiên/cache/outbox theo protocol
terminated -> khôi phục từ storage, không dựa biến RAM
background job -> có platform budget, retry/idempotency
Không lấy debug behavior làm bảo đảm release
~~~

### Permission matrix có cả từ chối vĩnh viễn
Tên trạng thái phụ thuộc API/plugin, không hardcode một enum chung cho mọi OS. Kiểm lần đầu, denied, settings change, limited access nếu có và revoke khi đang dùng; không loop prompt để ép người dùng.
~~~text
Feature giả: chọn ảnh ghi chú lớp (nếu bổ sung)
not asked -> giải thích + system prompt theo platform
denied -> fallback nhập text
restricted/permanent -> hướng dẫn settings khi phù hợp
revoked outside -> reload capability, không crash
app không cần ảnh -> không xin quyền chỉ để đủ demo
~~~

### System UI cần kiểm bằng công cụ phù hợp
Widget test không hiện permission dialog native thật. Integration Flutter có giới hạn với UI native, nên lập kế hoạch kiểm manual hoặc automation platform được cấp; báo đúng case chưa kiểm thay vì chỉ ảnh giả.

PRACTICE: Nộp permission inventory tối thiểu và lifecycle state diagram. Kiểm background/resume/kill trong target lab, phiên hết hạn khi resume và fallback khi từ chối; phân biệt test app với native UI.
Q: Quyền hệ điều hành nên xin khi nào?
+ Theo nhu cầu và giải thích đúng mục đích, xử lý từ chối
- Mọi quyền ngay khi mở
- Chỉ để đủ checklist
Q: App ở background có được bảo đảm chạy Dart timer mãi không?
+ Không
- Có nếu timer.periodic
- Có nếu giữ màn hình

## LESSON mobile-dev-12 | Đóng gói, cấu hình và phát hành có kiểm

### Release là artifact có danh tính
Ghi version/build number, target, toolchain và cấu hình. Debug chạy được chưa chứng minh release đúng; cần test artifact đã build trên thiết bị/target tương ứng, không phát hành cửa hàng trong bài tập này.

### Config public khác secret
API_BASE là địa chỉ cấu hình public, không phải nơi giấu credential. dart-define có thể xuất hiện trong artifact nên không chứa server key. Ví dụ localhost phải được ánh xạ cục bộ đúng target, không hardcode production.
~~~text
const apiBase=String.fromEnvironment('API_BASE',defaultValue:'http://localhost:3100');
// Chỉ cấu hình public; server secret không nằm trong app.
final uri=Uri.parse(apiBase);
// bootstrap phải validate scheme/origin theo config lab được cấp.
~~~

### Build theo nền tảng có điều kiện
Các lệnh là kế hoạch trên máy có toolchain thích hợp. iOS cần môi trường và signing hợp lệ theo nền tảng; không tự tạo key thật hay upload. Bảo quản signing material bằng quy trình dự án, không chép vào source/tài liệu.
~~~text
flutter analyze
flutter test
flutter build apk --release --dart-define=API_BASE=http://localhost:3100
# APK lab: test trên target phù hợp, localhost mapping riêng.
# Nền tảng khác: dùng build target tương ứng khi có toolchain.
# Không upload/publish hoặc đưa signing secret vào lệnh mẫu.
~~~

### Smoke release và rollback rõ
Cài đặt/nâng cấp/hạ cấp có giới hạn platform và storage migration. Rollback binary không tự khôi phục schema local đã đổi, nên thiết kế migration compatible hoặc kế hoạch tiến sửa; giữ artifact trước đã kiểm.

Ứng dụng thật cần HTTPS và xác minh chứng thư đúng; không vô hiệu hóa kiểm TLS toàn cục để hết lỗi. HTTP localhost chỉ cho lab cô lập theo platform config, không kéo ngoại lệ cleartext rộng sang release thật.

9. Lưu yêu cầu cục bộ không chứng minh server chấp nhận; giữ idempotency key ổn định theo một ý định và thể hiện trạng thái chờ.
10. Yêu cầu tối thiểu theo tính năng, kiểm denied/permanently denied theo platform và không chặn chức năng không liên quan.
11. Unit/widget/integration có phạm vi khác; integration_test cũng không trực tiếp điều khiển mọi native UI, cần công cụ/kế hoạch platform phù hợp.
12. Giá trị cấu hình có thể nằm trong artifact, không nhúng server secret; API base public khác credential cần bảo vệ.

### Rủi ro và lựa chọn phương án
13. Timeout không chứng minh server chưa ghi; cần idempotency và reconcile để không tạo đăng ký lặp hoặc báo sai kết quả.
14. Timeout của Future giới hạn chờ kết quả nhưng tác vụ gốc có thể tiếp tục; cancellation phụ thuộc client/API và quyền sở hữu tài nguyên.
15. Expanded giải constraints theo trục chính, không sửa mọi vấn đề chiều cao/nội dung; còn phải kiểm màn nhỏ, chữ lớn và RTL nếu hỗ trợ.
16. Người dùng cần biết trường nào và cách sửa, không dựa riêng màu sắc; kiểm screen reader và bàn phím theo target.

### Dự án, bằng chứng và bàn giao
17. Route là địa chỉ UI, request vẫn cần authorization; deep link không được bỏ qua login/resource checks.
18. Hệ điều hành có thể suspend/kill, background task có giới hạn; cần API/platform policy phù hợp và đồng bộ trạng thái khi resume.
19. Debug xanh không chứng minh release/profile, signing hay platform permissions đúng; promotion phải biết artifact nào đã được kiểm.
20. Khai báo target hỗ trợ và ca đã kiểm, không hứa mọi nền tảng từ một bản build; ghi giới hạn toolchain và native behavior.
