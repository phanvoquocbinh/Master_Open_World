## LESSON backend-01 | HTTP/REST: hợp đồng giữa hai phía

### Bài toán và cách nghĩ
Quầy đặt cơm của nhóm giả lập Mây Tre nhận yêu cầu, kiểm tra rồi trả biên nhận. API cũng cần hợp đồng: method, đường dẫn, body, mã trạng thái. REST tổ chức theo tài nguyên /orders; GET chỉ đọc, POST tạo mới. 201 biểu thị đã tạo; 204 không có body; 400 dữ liệu sai; 404 không tìm thấy. Khóa này dùng Node.js hỗ trợ ES module, Express 5 và Python với FastAPI/Pydantic 2; các thư viện phải cài trong môi trường thực hành riêng.

### Máy chủ Express tối thiểu
Lưu app.mjs, cài express trong thư mục bài, chạy node app.mjs. express.json giải mã JSON trước route; export app giúp kiểm thử mà không mở cổng. Khi chạy trực tiếp, dùng file server.mjs riêng import app rồi app.listen(3000). GET này trả một mảng JSON; dữ liệu chỉ ở bộ nhớ.
~~~js
import express from "express";
export const app = express();
app.use(express.json());
app.get("/orders", (req, res) => {
  res.json([{ id: 1, dish: "Cơm nấm" }]);
});
~~~

### Cùng hợp đồng với FastAPI
Lưu main.py, chạy fastapi dev main.py sau khi cài fastapi[standard]. Hàm trả list được chuyển thành JSON. Hai framework là hai lựa chọn thực hiện cùng hợp đồng, không chạy chung cổng cùng lúc.
~~~python
from fastapi import FastAPI
app = FastAPI()
@app.get("/orders")
def list_orders():
    return [{"id": 1, "dish": "Cơm nấm"}]
~~~

## LESSON backend-02 | Routing: path, query và thứ tự xử lý

### Bài toán và cách nghĩ
Path chỉ một tài nguyên, query lọc hoặc phân trang: /orders/7 khác /orders?status=open. Giống số phiếu gọi món khác điều kiện “chưa giao”. Phân biệt id không hợp lệ với id hợp lệ nhưng chưa có. Dữ liệu truy cập luôn phải kiểm quyền ở máy chủ, không chỉ ẩn nút ở giao diện.

### Tham số đường dẫn Express
Thêm vào app bài trước. Express cho req.params.id dưới dạng chuỗi; Number và Number.isSafeInteger tránh chấp nhận 7abc. Mảng cục bộ là dữ liệu giả. return ngăn gửi response lần hai.
~~~js
const orders = [{ id: 7, dish: "Bún nấm" }];
app.get("/orders/:id", (req, res) => {
  const id = Number(req.params.id);
  if (!Number.isSafeInteger(id) || id < 1) return res.status(400).json({ error: "invalid_id" });
  const order = orders.find(x => x.id === id);
  if (!order) return res.status(404).json({ error: "not_found" });
  res.json(order);
});
~~~

### Giới hạn query trong FastAPI
Đoạn độc lập, dùng thay route danh sách cũ. Annotated kèm Query giới hạn limit trong 1..50. Giá trị không đúng bị FastAPI từ chối với 422 trước khi vào hàm. Không dùng limit vô hạn làm tràn bộ nhớ.
~~~python
from typing import Annotated
from fastapi import Query
@app.get("/orders")
def list_orders(limit: Annotated[int, Query(ge=1, le=50)] = 10):
    rows = [{"id": 7, "dish": "Bún nấm"}]
    return rows[:limit]
~~~

### Ma trận đầu vào
Đây là hợp đồng kiểm thử đề xuất, không phải lệnh. Express bài này tự chọn 400; FastAPI mặc định 422 cho validation. Client phải theo hợp đồng đã công bố, không gán mọi 4xx thành 401.
~~~text
GET /orders/7          => 200 nếu tồn tại
GET /orders/999        => 404
GET /orders/abc        => 400 (Express mẫu)
GET /orders?limit=0    => 422 (FastAPI mẫu)
~~~

### Lỗi hay gặp và cách kiểm tra
Lỗi thường gặp: dùng parseInt("7abc") ra 7; khai báo route /orders/:id trước route tĩnh /orders/stats khiến stats bị coi là id; phân trang thiếu thứ tự ổn định làm trùng hoặc bỏ sót bản ghi.

PRACTICE: Thêm /orders/stats trước route :id và kiểm tra id 0, -1, abc, 7, 999. Với query hãy thử 1, 50, 51. Tiêu chí đạt: bảng kết quả rõ ràng và không lộ stack trace.
Q: req.params.id trong Express thường là kiểu gì?
+ Chuỗi cần kiểm tra trước khi dùng
- Luôn là số nguyên an toàn
- Luôn là object JSON
Q: id hợp lệ nhưng không tồn tại trả gì?
+ 404 theo hợp đồng tài nguyên

## LESSON backend-03 | Validate body và tạo tài nguyên

### Bài toán và cách nghĩ
Kiểm dữ liệu ở cửa vào giống người nhận phiếu kiểm tra số suất trước khi chuyển bếp. Kiểm cả kiểu và giới hạn: qty phải là số nguyên 1..20; dish là chuỗi không trắng, tối đa 80 ký tự. Không tin validate phía trình duyệt. Ví dụ chỉ lưu bộ nhớ; khởi động lại sẽ mất dữ liệu.

### Express: kiểm kiểu trước khi trim
Thêm vào app đã có express.json. Không gọi .trim() trên dữ liệu chưa chắc là chuỗi. Kiểm xong mới tạo đơn; id tăng cục bộ chỉ phù hợp bài học một tiến trình.
~~~js
const created = [];
app.post("/orders", (req, res) => {
  const { dish, qty } = req.body ?? {};
  if (typeof dish !== "string" || !dish.trim() || dish.trim().length > 80 || !Number.isInteger(qty) || qty < 1 || qty > 20) {
    return res.status(400).json({ error: "invalid_order" });
  }
  const row = { id: created.length + 1, dish: dish.trim(), qty };
  created.push(row);
  res.status(201).json(row);
});
~~~

### Pydantic 2: schema rõ ràng
Dùng StrictInt để không tự đổi chuỗi "2" thành số 2, giúp hợp đồng chặt như Express. str_strip_whitespace chạy trước kiểm độ dài; extra=forbid ngăn trường bất ngờ. Đây là đoạn thay thế route POST tương ứng.
~~~python
from pydantic import BaseModel, Field, ConfigDict, StrictInt
class OrderIn(BaseModel):
    model_config = ConfigDict(str_strip_whitespace=True, extra="forbid")
    dish: str = Field(min_length=1, max_length=80)
    qty: StrictInt = Field(ge=1, le=20)
@app.post("/orders", status_code=201)
def create_order(data: OrderIn):
    return {"id": 1, **data.model_dump()}  # chỉ minh họa, chưa lưu DB
~~~

### Gửi JSON tới localhost
PowerShell có thể lưu JSON trong file rồi dùng --data-binary để tránh vấn đề dấu nháy. Đây là nội dung request.json và lệnh minh họa; không có thông tin tài khoản.
~~~text
request.json: {"dish":"Cơm nấm","qty":2}
curl.exe -i http://localhost:3000/orders -H "Content-Type: application/json" --data-binary @request.json
# Kỳ vọng: 201; thử qty: "2" để quan sát từ chối
~~~

### Lỗi hay gặp và cách kiểm tra
Không kiểm giá tiền do client gửi rồi tin ngay: giá phải lấy từ dữ liệu phía server. Giới hạn kích thước body cũng cần cấu hình. FastAPI trả 422 theo mặc định; nếu muốn đồng nhất 400 phải thiết kế handler riêng và test, không sửa kỳ vọng tùy tiện.

PRACTICE: Lập bảng 7 trường hợp: dish trắng, thiếu dish, dish là số, qty chuỗi, qty 0, qty 21 và hợp lệ. Ghi phản hồi và chứng minh không tạo đơn lỗi.

- Vì HTML không hiển thị được chữ Việt

## LESSON backend-04 | SQL, transaction và ORM

### Bài toán và cách nghĩ
Bảng dữ liệu giống sổ đơn có khóa chính. SQL giúp truy vấn và ràng buộc; ORM ánh xạ bản ghi sang đối tượng nhưng không thay kiến thức transaction. Khi trừ tồn kho và tạo đơn phải cùng thành công hoặc cùng hủy. Ví dụ SQLite dùng file cục bộ; cần migration khi thay schema.

### Schema và tham số truy vấn
Schema dùng integer cents để tránh sai số tiền dạng float. CHECK bảo vệ ngay cả khi dữ liệu đi từ công cụ khác ngoài API. Không ghép chuỗi SQL từ tên món hoặc id của người dùng.
~~~sql
CREATE TABLE orders (
 id INTEGER PRIMARY KEY,
 dish TEXT NOT NULL,
 qty INTEGER NOT NULL CHECK(qty BETWEEN 1 AND 20),
 cents INTEGER NOT NULL CHECK(cents >= 0)
);
CREATE INDEX idx_orders_dish ON orders(dish);
~~~

### Node: prepared statement với SQLite tích hợp
Dùng Node có node:sqlite; API này phụ thuộc phiên bản runtime, kiểm trước khi thực hành. DatabaseSync chặn event loop nên hợp bài demo nhỏ. Dấu ? nhận giá trị, không nhận tên bảng. Chuỗi có dấu nháy vẫn là dữ liệu.
~~~js
import { DatabaseSync } from "node:sqlite";
const db = new DatabaseSync(":memory:");
db.exec("CREATE TABLE orders (id INTEGER PRIMARY KEY, dish TEXT NOT NULL)");
const insert = db.prepare("INSERT INTO orders(dish) VALUES (?)");
insert.run("Cơm nấm");
console.log(db.prepare("SELECT * FROM orders WHERE id = ?").get(1));
~~~

### Python: ORM SQLAlchemy 2
Cài SQLAlchemy; đoạn độc lập này tạo bảng trên DB bộ nhớ. Session có phạm vi ngắn; begin tự commit khi không lỗi và rollback khi có exception. Không chia sẻ một Session toàn cục cho nhiều request.
~~~python
from sqlalchemy import create_engine, String, select
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, Session
class Base(DeclarativeBase): pass
class Order(Base):
    __tablename__ = "orders"
    id: Mapped[int] = mapped_column(primary_key=True)
    dish: Mapped[str] = mapped_column(String(80))
engine = create_engine("sqlite:///:memory:")
Base.metadata.create_all(engine)
with Session(engine) as session, session.begin():
    session.add(Order(dish="Cơm nấm"))
with Session(engine) as session:
    print(session.scalars(select(Order)).all())
~~~

### Lỗi hay gặp và cách kiểm tra
N+1 là một query lấy danh sách rồi mỗi dòng lại query chi tiết; dùng join/eager loading có đo đạc. Index làm đọc nhanh hơn cho một số truy vấn nhưng tốn ghi và dung lượng. Cú pháp ORM không tự ngăn SQL injection nếu bạn tự ghép SQL thô.

PRACTICE: Tạo 3 đơn và truy vấn theo id bằng tham số. Thử tên món có dấu nháy; giải thích vì sao không làm hỏng query. Viết mô tả transaction trừ tồn kho + tạo đơn, kể tình huống bước hai thất bại.
Q: Transaction giúp điều gì?
+ Các thay đổi liên quan cùng commit hoặc rollback
- Mọi truy vấn luôn nhanh hơn
- Không cần backup nữa
Q: Cách truyền dữ liệu người dùng vào SQL đúng?
+ Dùng tham số bind
- Nối chuỗi trực tiếp
- Xóa dấu cách là đủ

## LESSON backend-05 | Xác thực session/JWT và phân quyền

### Bài toán và cách nghĩ
Xác thực trả lời “ai”, phân quyền trả lời “được làm gì”. Session lưu trạng thái ở server và cookie giữ mã tham chiếu; JWT chứa claim có chữ ký, không phải dữ liệu được mã hóa. Không viết thuật toán ký hoặc hàm băm mật khẩu tự chế. Mẫu dùng đối tượng người dùng giả để tập kiểm quyền, không phải hệ thống đăng nhập hoàn chỉnh.

### Express: quyền sở hữu ở server
Giả sử middleware xác thực tin cậy đã đặt req.user. Mẫu không đọc ownerId từ body. Nếu thiếu principal trả 401; tài nguyên của người khác trả 403 theo hợp đồng mẫu; có hệ thống chọn 404 để hạn chế dò tài nguyên.
~~~js
app.get("/private/orders/:id", (req, res) => {
  if (!req.user) return res.sendStatus(401);
  const row = { id: 1, ownerId: 42, dish: "Cơm nấm" };
  if (row.ownerId !== req.user.id) return res.sendStatus(403);
  res.json(row);
});
~~~

### FastAPI: kiểm claim sau xác minh chữ ký
Đoạn độc lập cần PyJWT. key đến từ biến môi trường cấu hình riêng; không có khóa thật trong bài. algorithms cố định, kiểm issuer/audience/exp/sub. Không lấy thuật toán từ header token. Kết quả sub còn cần tra người dùng và trạng thái tài khoản.
~~~python
import os, jwt
key = os.environ["JWT_VERIFY_KEY"]
def verify_token(token: str):
    return jwt.decode(token, key, algorithms=["RS256"],
        audience="orders-api", issuer="classroom",
        options={"require": ["exp", "sub", "iss", "aud"]})
~~~

### Chọn session hay JWT
Bảng là hướng dẫn thiết kế, không chứa mã đăng nhập. Cookie session cần HttpOnly, Secure khi HTTPS, SameSite phù hợp và phòng CSRF cho hành động thay đổi trạng thái. JWT cần hạn dùng, xoay khóa và chiến lược thu hồi; logout client không tự vô hiệu mọi token.
~~~text
Session: cookie mã ngẫu nhiên -> kho session -> user
JWT: token -> xác minh chữ ký + claims -> user
401: thiếu/sai/hết hạn bằng chứng xác thực
403: đã xác thực nhưng không được phép
~~~

### Lỗi hay gặp và cách kiểm tra
Lỗi hay gặp: decode JWT mà không verify; lưu mật khẩu thuần; log Authorization; chỉ kiểm role mà quên owner; dùng khóa bí mật mặc định trong source. Cấu hình CORS không thay thế xác thực hoặc CSRF. Dùng thư viện băm mật khẩu phù hợp như Argon2, tham số được kiểm thử.

PRACTICE: Tạo ma trận quyền cho khách, chủ đơn, người khác và quản trị viên. Với mỗi vai ghi status và dữ liệu được xem. Mô tả cách test token hết hạn và logout session mà không ghi token thật vào tài liệu.
Q: JWT được ký có mặc định giữ kín payload không?
+ Không, payload có thể đọc được
- Có, mọi claim đều được mã hóa
- Chỉ kín khi dùng Base64
Q: Đơn của người khác cần kiểm ở đâu?
+ Phía server trên từng tài nguyên
- Chỉ trên nút giao diện
- Trong localStorage do client tự đặt

## LESSON backend-06 | Xử lý lỗi và log có cấu trúc

### Bài toán và cách nghĩ
Quầy tiếp nhận cần báo lỗi dễ hiểu cho khách, đồng thời giữ thông tin chẩn đoán cho đội vận hành. Client nhận mã lỗi ổn định và request id; log nội bộ ghi ngữ cảnh tối thiểu, không chứa mật khẩu/token/body nhạy cảm. Không trả nguyên exception hoặc stack trace ra mạng.

### Express 5: handler lỗi đặt cuối
Đặt sau mọi route. Express 5 chuyển Promise bị reject trong async handler tới middleware lỗi; callback bất đồng bộ ngoài chuỗi Promise vẫn cần next(err). res.headersSent tránh ghi response lần hai. Ví dụ cố ý không log err.message vì message có thể chứa dữ liệu đầu vào.
~~~js
import { randomUUID } from "node:crypto";
app.use((err, req, res, next) => {
  if (res.headersSent) return next(err);
  const requestId = randomUUID();
  console.error(JSON.stringify({ requestId, kind: err.name, status: 500 }));
  res.status(500).json({ error: "internal_error", requestId });
});
~~~

### FastAPI: lỗi nghiệp vụ dự đoán được
HTTPException dùng cho lỗi nghiệp vụ như thiếu tài nguyên. Không bọc toàn bộ ứng dụng bằng except rồi trả 200. Các lỗi không dự đoán cần handler riêng theo chính sách log của hệ thống.
~~~python
from fastapi import HTTPException
@app.get("/catalog/{item_id}")
def read_item(item_id: int):
    if item_id != 1:
        raise HTTPException(status_code=404, detail="item_not_found")
    return {"id": 1, "name": "Cơm nấm"}
~~~

### Log an toàn để lần theo yêu cầu
Đây là bản ghi giả. severity cho mức nghiêm trọng; requestId nối nhiều sự kiện cùng request. Không đưa user id hay request id thành nhãn metric cardinality cao. Không tin request id từ client nếu chưa giới hạn ký tự/độ dài.
~~~json
{"event":"order_failed","severity":"error","requestId":"demo-request-07","status":500,"durationMs":83}
{"event":"order_created","severity":"info","requestId":"demo-request-08","status":201,"durationMs":24}
~~~

### Lỗi hay gặp và cách kiểm tra
Log cả req.headers sẽ lộ cookie/token; log nguyên body dễ lộ địa chỉ khách. Catch rồi im lặng làm lỗi mất dấu. Không coi mọi 404 là sự cố khẩn; phân biệt lỗi người dùng, sự cố phụ thuộc và lỗi lập trình để cảnh báo phù hợp.

PRACTICE: Cố ý ném Error trong một route Express async, xác nhận client nhận 500 không có stack trace và có requestId. Kiểm log không chứa header Authorization hay body. Với FastAPI kiểm 404 dự đoán được.
Q: Handler lỗi Express cần mấy tham số?
+ Bốn: err, req, res, next
- Hai: req, res
- Một: err
Q: Log nào nên tránh?
+ Toàn bộ Authorization và Cookie
- Mã sự kiện không nhạy cảm
- Thời gian xử lý

## LESSON backend-07 | Unit test và integration test cho API

### Bài toán và cách nghĩ
Unit test kiểm một hàm như tính tiền; integration test gửi request qua routing, validate và response. Giống kiểm cân riêng rồi kiểm cả quy trình bán hàng. Test phải độc lập, tạo dữ liệu riêng và kiểm cả đường lỗi, quyền truy cập, tác dụng phụ. Không gọi API bên ngoài thật trong unit test.

### Unit test Node tích hợp
Lưu pricing.mjs export hàm total như dưới, test ở pricing.test.mjs bằng node:test. Chạy node --test. RangeError biểu thị input không hợp lệ; số tiền nguyên theo đơn vị nhỏ nhất giúp so sánh chính xác.
~~~js
// pricing.mjs
export function total(unit, qty) {
  if (!Number.isInteger(unit) || unit < 0 || !Number.isInteger(qty) || qty < 1) throw new RangeError("invalid_input");
  return unit * qty;
}
// pricing.test.mjs (file riêng)
import test from "node:test";
import assert from "node:assert/strict";
import { total } from "./pricing.mjs";
test("3 phần giá 25000", () => assert.equal(total(25000, 3), 75000));
test("không nhận qty 0", () => assert.throws(() => total(25000, 0), RangeError));
~~~

### Integration test Express với Supertest
Cài supertest trong môi trường bài; app.mjs chỉ export app, không listen. Supertest xử lý server test. Đừng chỉ kiểm 200: xác nhận Content-Type, schema và giá trị quan trọng.
~~~js
import test from "node:test";
import assert from "node:assert/strict";
import request from "supertest";
import { app } from "./app.mjs";
test("GET trả đúng hợp đồng", async () => {
  const r = await request(app).get("/orders").expect(200).expect("Content-Type", /json/);
  assert.ok(Array.isArray(r.body));
  assert.equal(r.body[0].id, 1);
});
~~~

### FastAPI TestClient và pytest
Cài pytest và httpx; lưu test_main.py cạnh main.py. Test POST này tương ứng schema OrderIn ở bài 3. Không phụ thuộc dữ liệu từ test chạy trước. Khi thêm DB phải dùng DB test và override dependency, không ghi vào DB làm việc.

## LESSON backend-08 | Hiệu năng, cache và giới hạn tải

### Bài toán và cách nghĩ
Đo trước khi tối ưu: throughput là số request/giây; p95 là thời gian mà 95% request không vượt quá; tỷ lệ lỗi cần đi cùng độ trễ. Cache như chuẩn bị sẵn món phổ biến nhưng phải biết khi nào món không còn mới. Không cache dữ liệu riêng của nhiều người dưới một khóa chung.

### Cache TTL đơn giản cho dữ liệu công khai
Đoạn độc lập minh họa nguyên tắc, không phải cache phân tán. performance.now đo thời gian đơn điệu. Hàm readCatalog được tiêm để tránh phụ thuộc DB cụ thể; sau cập nhật dữ liệu, gán entry=null để vô hiệu.
~~~js
let entry = null;
export async function cachedCatalog(readCatalog) {
  const now = performance.now();
  if (entry && entry.until > now) return entry.value;
  const value = await readCatalog();
  entry = { value, until: performance.now() + 5000 };
  return value;
}
export function invalidateCatalog() { entry = null; }
~~~

### Python: đo đoạn xử lý
perf_counter phù hợp đo thời lượng, không dùng làm giờ lịch. Ví dụ lặp 100 lần; muốn đo API thật phải có tải đồng thời và mẫu đại diện. Không suy ra p95 tin cậy từ vài request thủ công.
~~~python
from time import perf_counter
def measure(fn):
    start = perf_counter()
    value = fn()
    return value, (perf_counter() - start) * 1000
value, ms = measure(lambda: sum(range(10000)))
print({"durationMs": round(ms, 3), "value": value})
~~~

### Ngân sách hiệu năng và kiểm tải
Các số dưới đây là mục tiêu giả cho lớp, không phải chuẩn áp cho mọi sản phẩm. Cache hit ratio cao vẫn có thể trả dữ liệu cũ; kiểm tính đúng và invalidation sau cập nhật. Rate limit thường trả 429 và Retry-After phù hợp.
~~~text
Tải mẫu: 20 người dùng đồng thời, 5 phút
Mục tiêu giả: p95 < 300 ms; lỗi < 1%
Đo thêm: DB query count, CPU, bộ nhớ, cache hit/miss
Thử: cold cache, warm cache, cache lỗi, cập nhật giá
Giới hạn: 100 request/phút/người dùng (mô phỏng)
~~~

### Lỗi hay gặp và cách kiểm tra
Lỗi hay gặp: cache không giới hạn số khóa, TTL quá dài, cache dữ liệu từng tài khoản bằng khóa /profile, nhiều request cùng cache miss gây dồn tải. Cân nhắc gộp request đang chờ, timeout và giới hạn tài nguyên; không retry vô hạn khi phụ thuộc đang lỗi.

PRACTICE: Dùng fake readCatalog đếm số lần gọi. Gọi hai lần trong TTL phải đọc nguồn một lần; sau invalidate phải đọc lại. Viết báo cáo nêu tải, p50/p95, lỗi và giới hạn thử nghiệm; không tự bắn tải vào host bên ngoài.
Q: p95 nghĩa là gì?
+ 95% mẫu có thời gian không vượt ngưỡng đó
- Mọi request đúng 95 mili giây
- Tỷ lệ cache hit luôn là 95%
Q: Khóa cache /profile chung nguy hiểm vì sao?
+ Có thể trả dữ liệu người này cho người khác
- Vì URL quá ngắn
- Vì TTL không bao giờ hết

## LESSON backend-09 | Transaction đồng thời và idempotency

### Bất biến phải giữ khi nhiều người cùng ghi
API trung tâm giả định Thoi Vân còn một chỗ nhưng hai học viên có thể cùng đọc remaining1. Transaction không tự sửa kiểu read-modify-write sai;đặt kiểm quota ở một cập nhật nguyên tử rồi kiểm số dòng được nhận.

### Conditional update theo dialect PostgreSQL
Schema lab có remaining nguyên không âm. Câu UPDATE dưới trả một dòng khi lấy được chỗ,không dòng khi hết hoặc không có lớp;service cần phân loại theo quyền/hợp đồng và rollback phần khác nếu không thể hoàn tất.
~~~sql
UPDATE classes SET remaining=remaining-1
WHERE id=$1 AND remaining>0
RETURNING id,remaining;
-- $1 là tham số do driverbind,không nối input vào SQL.
-- INSERT enrollment và các ghi liên quan ở cùngtransaction.
~~~

### Khóa chống lặp cần scope và fingerprint
Bảng ý định ràng actor/key duy nhất,hash để phát hiện cùng key khác payload. Đây là schema tối giản:không lưu secret,phải thiết kế TTL,status/kết quả và xử lý cạnh tranh;hash không thay validation quyền.
~~~sql
CREATE TABLE idempotency (
 actor_id TEXT NOT NULL, request_key TEXT NOT NULL,
 payload_hash TEXT NOT NULL, response_json JSONB,
 PRIMARY KEY(actor_id,request_key)
);
~~~

### Thứ tự trong service cần cơ chế nguyên tử
Pseudocode mô tả hợp đồng adapter,không phải thư viện có sẵn. Reservation key,quota,enrollment,outbox và response cache cùng transaction lab;request cạnh tranh cùng key phải đợi/đọc kết quả theo engine,không commit một pending vô chủ.
~~~text
BEGIN
reserve(actor,key,hash) hoặc đọc kết quả đã commit
if key tồn tại:verify hash,return same result theo rule
else:take seat atomically;insert enrollment/outbox
store result for key
COMMIT; nếu lỗi trước commit thì ROLLBACK
Timeout saucommit:client dùng lại key hoặc query status
~~~

### Kiểm đúng cơ chế dưới cạnh tranh
Dùng barrier lab cho hai request tranh chỗ cuối và hai request cùng key. Assert response cả hai,recordcount và remaining saucommit;thử crash trước/saucommit,không chỉ một POST tuần tự xanh.

PRACTICE: Bổ sung transaction/idempotency choAPI lab,có actor/key/hash và conditional quota. Nộp sáuca cạnh tranh/retry/payloadconflict cùng snapshot trước/sau,ghi policy businesserror/TTL và điểm rollback.
Q: Hai request tranh chỗ cuối nên cập nhật thế nào?
+ Có kiểm nguyên tử và affected rows theo thiết kế
- Đọc remaining rồi ghi giá trị cũ trừ1
- Chỉ khóa nút UI
Q: Idempotency key cần ràng buộc với gì?
+ Actor,ý định và payload theo hợp đồng
- Mỗi retry key mới
- Mọi giao dịch cùng key
Q: Timeout client sauPOST có chứng minh server chưa commit không?
+ Không
- Có luôn
- Có nếu trình duyệt đóng

## LESSON backend-10 | Tác vụ nền, outbox và xử lý trùng

### Ghi ý định gửi trong cùng database
Sau tạo enrollment,worker cần gửi thông báo. Nếu ghi DB rồi gọi broker ở hai bước riêng,có thể mất thông báo khi crash;outbox ghi enrollment và sự kiện cùng transaction cục bộ,relay đọc saucommit.

### Bảng outbox cần định danh và trạng thái
Schema PostgreSQL lab lưu eventId duy nhất và payload tối thiểu. Thiết kế published/lease/retry cho relay cần được chốt ngoài schema này;không khẳng định mỗi event chỉ được gửi một lần.
~~~sql
CREATE TABLE outbox (
 event_id TEXT PRIMARY KEY, aggregate_id TEXT NOT NULL,
 kind TEXT NOT NULL,payload JSONB NOT NULL,
 created_at TIMESTAMPTZ NOT NULL DEFAULT now(),published_at TIMESTAMPTZ
);
~~~

### Transaction phát sinh dữ liệu và event
Đoạn SQL là ảnh cấu trúc,tham số đúng driver. Nếu insert outbox fail,rollback enrollment và quota trong cùng transaction;gọi email/provider ngoài không nằm trongrollback này.
~~~sql
BEGIN;
-- Sau bướcquota đãđược bảo vệ:
INSERT INTO enrollments(id,class_id,student_id,status) VALUES($1,$2,$3,'confirmed');
INSERT INTO outbox(event_id,aggregate_id,kind,payload) VALUES($4,$1,'EnrollmentConfirmed',$5);
COMMIT;
~~~

### Consumer idempotent vẫn cần thiết
Relay có thể gửi rồi crash trước đánh dấu published.Consumer local có thể dùng processed_events unique cùng transaction với tác dụng DB;nếu tác dụng ngoài như email,cần provider key/ledger và reconciliation phù hợp.
~~~text
receive E7
BEGIN:claim E7 cho consumerC,apply local effect,COMMIT
duplicate E7 ->không áp lại local effect
ack sau khi đủ điều kiện theo brokercontract
external send:thiết kế riêng,không claim DBrollback hoàn tác email
~~~

### Kiểm mất,lặp và sai thứ tự
Crash saubusinesscommit,trước publish,sau publish/trước mark là các điểm khác nhau. Đối soát enrollment/outbox/consumerledger và kết quả cuối;event đến muộn cần version/order rule chứ không dedup chỉ theo type.

PRACTICE: Nộp outbox/relay/consumer contract và crashmatrix sáu điểm. Thực hiện trên lab bằng queue stub hoặc DB riêng,có duplicate/out-of-order và giới hạn tác dụng ngoài,chưa nhận exactly-once toàn hệ thống.
Q: Outbox giải quyết khoảng trống nào?
+ Ghi dữ liệu và ý định phát sự kiện cùng transaction cục bộ
- Tự bảo đảm broker không lỗi
- Tự đúng một lần mọi tác dụng ngoài
Q: Consumer nhận event hai lần nên làm gì?
+ Kiểm trùng và tác dụng trong cùng phạm vi nguyên tử khi phù hợp
- Áp tác dụng hai lần
- Bỏ mọi event giống type
Q: Email gửi ngoài database có nằm trong transaction DB không?
+ Không
- Có nếu gọi trước COMMIT
- Có nếu function async

## LESSON backend-11 | Tương thích API, migration và rollout

Thêm field nullable trước,chuyển writer/reader theo kế hoạch rồi backfill và kiểm. Constraint hoặc drop cuối cần cơ chế engine thích hợp,có backup/restore;không gọi SQL ngắn là migration production hoàn chỉnh.

## LESSON backend-12 | Quan sát, deadline và giới hạn phụ thuộc

### Request có ngân sách xuyên phụ thuộc
API gọi database và notification có thể tích lũy timeout/retry vượt thời gian người dùng chờ. Chốt deadline,phân bổ ngân sách còn lại,giới hạn concurrency và phân loại lỗi;không mỗi tầng tự đợi30 giây bấtchấp cả luồng.

### Abort là cơ chế hợp tác
Fetch Node hỗ trợ signal,nhưng hủy client không bảo đảm server chưa commit. Mã minh họa chỉ đọc dependency lab;với thao tác ghi cần idempotency và đối soát trạng thái.
~~~js
const controller=new AbortController();
const timer=setTimeout(()=>controller.abort(),600);
try{
 const r=await fetch('http://localhost:3200/notify-status',{signal:controller.signal});
 if(!r.ok)throw new Error(`dependency_${r.status}`);
 return await r.json();
}finally{clearTimeout(timer);}
~~~

### Metric và log đủ liên kết
Latency,error,rate,saturation theoendpoint/flow hữu hạn giúp điều tra.Correlationid trong log không nên thành tag vô hạn;không log Authorization/body nhạy cảm,trạng thái nghiệp vụ phải được đo riêng khi cần.
~~~text
{"requestId":"REQ-LAB-7","route":"POST enrollment","status":201,"durationMs":84,"outcome":"confirmed"}
metric labels:route/status/outcome hữu hạn
Không tag mỗi studentId hoặc requestId vào mọi timeseries
~~~

### Giảm lỗi dây chuyền bằng giới hạn
Bulkhead/concurrencycap,timeout,boundedretry và circuit state có thể hữu ích theo thiết kế. Chúng không tự sửa quorum/quyền/nghiệp vụ;cần kiểm nhánh mở/hồi phục và response khiqueue đầy.
~~~text
dependency503 ->retry có budget nếu thao tác đủ điều kiện
queue đầy ->từ chối có kiểm soát theo contract
deadline hết ->dừng chờ/hủy khi hỗ trợ
recovery ->half-open/closed theo thiết kế lab
Không retry mọi4xx hoặc ghi không chống lặp
~~~

### Readiness khác process sống
Readiness lab có thể gồm schema đúng và dependency cần thiết,song liveness không nên tự restart mọi khiexternal lỗi gây vòng lặp. Ghi định nghĩa,probe và tác động routing theo hạ tầng đã chốt.

## LESSON backend-14 | Ôn tập & Thi cuối khoá

### Nền tảng và cách dùng công cụ
1. HTTP là giao thức,hợp đồng nghiệp vụ cần rõ dữ liệu,quyền,lỗi và tác dụng phụ.
2. Kiểm quy tắc matching của framework,đặt route và validation có chủ đích,không dùng tên path thay phân quyền.
3. Dữ liệu qua trust boundary phải được kiểm ở server,không tin validation UI hoặc kiểu tĩnh client.
4. Transaction cần thiết kế cách giữ invariant dưới cạnh tranh;kiểm hai phiên và lỗi giữa các bước.

### Dữ liệu và điều kiện biên
5. Cần xác minh chữ ký/thuộc tính theo thiết kế và kiểm quyền hiện tại;không tin claim chỉ vì đọc được JSON.
6. Giữ khả năng điều tra mà tránh rò quyền;response public không trả stacktrace hoặc chi tiết nội bộ không cần thiết.
7. Unit test với double kiểm logic trong điều kiện giả,phải có integration với schema/transaction thật của lab.
8. Cache phải giữ semantics quyền và nhất quán theo hợp đồng;hitcache không thay validation quyền.

### Tính đúng và cách điều tra
9. ConditionalUPDATE hoặc cơ chế khóa phù hợp bảo vệ quota;unique và transaction giữ thêm bấtbiến khác.
10. Cùng key khác payload cần xử lý xung đột,scope/TTL và kết quả retry phải được chốt.
11. Server có thể đã ghi trước response mất,nên truy trạng thái hoặc retry an toàn thay vì tạo ý định mới mù.
12. Relay có thể phát lặp,cần consumer idempotent và reconciliation;outbox không xóa mọi vấn đề phân tán.

### Rủi ro và lựa chọn phương án
13. Dedup theoeventId/consumer và hợp đồng,không bỏ nhầm update mới cùng loại;điểm ack/crash phải được kiểm.
14. Tác dụng ngoài cần idempotency/provider contract hoặc ledger/reconciliation riêng,không claim rollbackDB hoàn tác email.
15. Thêm trước,chuyển đọc/ghi có kiểm,backfill rồi thu gọn khioldreader không còn,có đối soát và phục hồi.
16. Schema/data đã đổi và write mới cần kế hoạch riêng,backup/restore và compatibility phải được thử.

### Dự án, bằng chứng và bàn giao
17. Timeout/retry cộngdồn có thể vượt ngân sách,giới hạn concurrency và hủy hợp tác theo khả năng dependency.
18. Phân loại lỗi,tổng budget,backoff/jitter và idempotency,tránh nhiều tầng retry nhân nhau.
19. Liveness và readiness có mục đích khác,không để dependency lỗi là restartloop mù hoặc nhận traffic khi schema chưa đúng.
20. Bằng chứng phải gắn fixture/version vàca âm,ghi rõ lab/stub,chưa suy productionready từ một demo.
