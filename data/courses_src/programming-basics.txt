## LESSON programming-basics-01 | Chương trình là gì? Chạy file JavaScript đầu tiên

### Chương trình giống một công thức nấu ăn
Một chương trình là danh sách chỉ dẫn mà máy tính làm theo từng bước, từ trên xuống dưới.
Giống công thức nấu mì: đun nước, cho mì vào, đợi 3 phút, thêm gia vị.
• Máy tính rất chăm chỉ nhưng không tự đoán ý bạn: viết sai một dấu là nó dừng và báo lỗi.
• JavaScript (JS) là ngôn ngữ ta dùng để viết chỉ dẫn.
• Node.js là "đầu bếp" đọc và thực hiện file .js trên máy bạn (không cần trình duyệt).
Vì sao tester học JS? Playwright, Postman tests, k6, WebdriverIO đều dùng JavaScript/TypeScript.
Chuẩn bị: đã cài Node.js và VS Code (khóa Máy tính & dòng lệnh, phòng 101).

Giải thích từng dòng:

## LESSON programming-basics-02 | Biến và kiểu dữ liệu

### Biến là chiếc hộp có dán nhãn
Biến giúp bạn đặt tên cho một giá trị để dùng lại nhiều lần.
Giải thích từng dòng:
• dòng 1: const tạo hộp tên baseUrl, bỏ vào một địa chỉ web. const = hằng số, không được đổi giá trị sau này.
• dòng 2: let tạo hộp retryCount có giá trị 0. let cho phép thay đổi về sau.
• dòng 3: lấy giá trị cũ cộng 1 rồi bỏ lại vào hộp, giờ là 1.
• dòng 4–5: in giá trị hai hộp.
Kết quả mong đợi:
http://localhost:3130
1
Quy tắc: mặc định dùng const, chỉ dùng let khi chắc chắn cần đổi giá trị. Không dùng var (cách cũ).
~~~js
const baseUrl = "http://localhost:3130";
let retryCount = 0;
retryCount = retryCount + 1;
console.log(baseUrl);
console.log(retryCount);
~~~

### Các kiểu dữ liệu cơ bản
Giải thích từng dòng:
• string (chuỗi): chữ, nằm trong nháy "..." hoặc '...'.
• number (số): 200, 3.14, -5, không có nháy.
• boolean: chỉ có true (đúng) hoặc false (sai), dùng cho trạng thái có/không.
• null: "cố tình để trống", ví dụ chưa có token.
• undefined: "chưa từng gán gì", như lastError.
• typeof cho biết kiểu của giá trị.
Kết quả mong đợi:
string number boolean
null undefined
~~~js
const username = "tester01";
const statusCode = 200;
const isLoggedIn = true;
let token = null;
let lastError;
console.log(typeof username, typeof statusCode, typeof isLoggedIn);
console.log(token, lastError);
~~~

### Bẫy chuyển kiểu mà tester hay gặp
Giải thích từng dòng:
• "5" + 1 cho "51": dấu + gặp chuỗi thì NỐI chứ không cộng.
• "5" - 1 cho 4: dấu - ép chuỗi thành số.
• Number("200") đổi chuỗi thành số, so sánh với 200 cho true.
• Number("abc") cho NaN (Not a Number), không đổi được.
• String(404) đổi số thành chuỗi "404", .length là số ký tự: 3.
Ý nghĩa với tester: dữ liệu đọc từ file CSV hay ô input luôn là chuỗi. Nhớ đổi sang số trước khi tính toán hoặc so sánh.
~~~js
console.log("5" + 1);
console.log("5" - 1);
console.log(Number("200") === 200);
console.log(Number("abc"));
console.log(String(404).length);
~~~

### Lỗi thường gặp
• Assignment to constant variable: cố đổi giá trị một const. Đổi thành let nếu thật sự cần thay đổi.
• is not defined: dùng biến chưa tạo, hoặc sai chữ hoa/thường (username khác userName).
• has already been declared: tạo cùng một tên biến hai lần. Lần sau chỉ gán lại (count = 2), không viết let nữa.
~~~text

~~~

## LESSON programming-basics-03 | Điều kiện: if, else và phép so sánh

### if giống biển chỉ đường
Chương trình cần ra quyết định: nếu điều kiện đúng thì đi đường A, ngược lại đi đường B.
Giải thích từng dòng:
• dòng 1: giả lập status code nhận được từ API.
• dòng 3: if kiểm tra điều kiện trong ngoặc tròn. === nghĩa là "bằng chính xác".
• dòng 4: chỉ chạy khi điều kiện đúng. Code bên trong ngoặc nhọn {} gọi là khối lệnh.
• dòng 5: else = "ngược lại".
• dòng 6: chỉ chạy khi điều kiện sai.
Kết quả mong đợi: PASS: API trả về thành công. Thử đổi 200 thành 500 và chạy lại.
~~~js
const statusCode = 200;

if (statusCode === 200) {
  console.log("PASS: API trả về thành công");
} else {
  console.log("FAIL: status code là " + statusCode);
}
~~~

### Các phép so sánh
Giải thích từng dòng:
• === so sánh cả giá trị và kiểu: true.
• 200 === "200": số và chuỗi khác kiểu nên false.
• == chỉ so giá trị, tự ép kiểu nên true. Dễ gây bug ẩn.
• !== "khác": true.
• > lớn hơn, < nhỏ hơn, >= lớn hơn hoặc bằng, <= nhỏ hơn hoặc bằng.
Kết quả mong đợi: true, false, true, true, true, false.
Quy tắc cho tester: luôn dùng === và !==. Giống kiểm tra hàng: phải đúng cả mã hàng lẫn loại hàng.
~~~js
console.log(200 === 200);
console.log(200 === "200");
console.log(200 == "200");
console.log(404 !== 200);
console.log(1500 > 1000);
console.log(3 <= 2);
~~~

### Nhiều nhánh với else if
Giải thích từng dòng:
• dòng 3: kiểm tra nhóm 2xx. && nghĩa là VÀ: cả hai điều kiện phải đúng.
• dòng 5: nếu nhánh trên sai, thử tiếp nhóm 4xx.
• dòng 7: tiếp tục thử nhóm 5xx.
• dòng 9: không khớp nhánh nào thì chạy else.
Máy kiểm tra từ trên xuống, gặp nhánh đúng đầu tiên thì chạy nhánh đó và bỏ qua phần còn lại.
Kết quả mong đợi: Lỗi phía client (4xx).
~~~js
const status = 404;

if (status >= 200 && status < 300) {
  console.log("Thành công (2xx)");
} else if (status >= 400 && status < 500) {
  console.log("Lỗi phía client (4xx)");
} else if (status >= 500) {
  console.log("Lỗi phía server (5xx)");
} else {
  console.log("Mã khác");
}
~~~

### Kết hợp điều kiện: VÀ, HOẶC, PHỦ ĐỊNH
Giải thích từng dòng:
• && (VÀ): đúng khi cả hai vế đúng. Ở đây role là viewer nên không in.
• || (HOẶC): đúng khi ít nhất một vế đúng. viewer không khớp vế nào nên không in.
• ! (PHỦ ĐỊNH): đảo ngược. !false thành true nên in dòng cuối.
• Khi khối lệnh chỉ có một dòng, có thể viết ngay sau if không cần {}, nhưng người mới nên luôn dùng {} cho rõ ràng.
Kết quả mong đợi: chỉ một dòng Hệ thống đang hoạt động.
Đây chính là cách nghĩ khi test phân quyền: mỗi vai trò thấy gì, không thấy gì.
~~~js
const isLoggedIn = true;
const role = "viewer";
const isMaintenance = false;

if (isLoggedIn && role === "admin") console.log("Hiện nút Xóa");
if (role === "admin" || role === "editor") console.log("Cho phép sửa");
if (!isMaintenance) console.log("Hệ thống đang hoạt động");
~~~

### Lỗi thường gặp
Giải thích:
• Một dấu = là GÁN giá trị, không phải so sánh. Viết status = 200 trong if sẽ gán 200 vào status.
• Với const, Node báo lỗi ngay. Với let, code chạy "êm" và luôn in PASS, kiểu bug nguy hiểm nhất với tester: test xanh nhưng sai.
• Cách sửa: dùng ===.
Lỗi khác: SyntaxError: Unexpected token 'else' do thừa dấu ; sau if (...) hoặc thiếu dấu } trước else. Bấm Shift+Alt+F trong VS Code để format, các khối lệnh sẽ thẳng hàng và dễ phát hiện ngoặc thiếu.
~~~js
const status = 500;
if (status = 200) {
  console.log("PASS");
}
// TypeError: Assignment to constant variable.
// Nếu status là let: không báo lỗi nhưng LUÔN in PASS (bug ẩn!)
~~~

## LESSON programming-basics-04 | Vòng lặp: làm lại nhiều lần không mỏi tay

### Vì sao cần vòng lặp?
Tester thường phải kiểm tra cùng một việc với nhiều bộ dữ liệu: 5 email, 10 mật khẩu, 100 user.
Viết tay 100 lần là cực hình. Vòng lặp giống máy dập: cài đặt một lần, chạy bao nhiêu lần cũng được.
Giải thích các phần trong ngoặc của for:
• let i = 1: điểm bắt đầu, biến đếm i bằng 1.
• i <= 3: điều kiện tiếp tục, còn đúng thì còn lặp.
• i++: sau mỗi vòng, tăng i thêm 1.
• Thân vòng lặp trong {} chạy mỗi vòng một lần.
Kết quả mong đợi:
Chạy test lần thứ 1
Chạy test lần thứ 2
Chạy test lần thứ 3
~~~js
for (let i = 1; i <= 3; i++) {
  console.log(`Chạy test lần thứ ${i}`);
}
~~~

### for...of: duyệt từng phần tử của danh sách
Giải thích từng dòng:
• dòng 1: danh sách 4 email cần kiểm tra (học kỹ về mảng ở bài 6).
• dòng 3: for...of lấy lần lượt từng email bỏ vào biến email.
• dòng 4: includes kiểm tra chuỗi có chứa ký tự đó không. Ở đây yêu cầu có cả @ và dấu chấm (quy tắc đơn giản cho ví dụ).
• dòng 5: email || "(rỗng)" in chữ (rỗng) khi email trống. điều_kiện ? A : B là if/else viết gọn.
Kết quả mong đợi:
a@example.com -> hợp lệ
b@test -> không hợp lệ
c@example.com -> hợp lệ
(rỗng) -> không hợp lệ
~~~js
const emails = ["a@example.com", "b@test", "c@example.com", ""];

for (const email of emails) {
  const valid = email.includes("@") && email.includes(".");
  console.log(`${email || "(rỗng)"} -> ${valid ? "hợp lệ" : "không hợp lệ"}`);
}
~~~

### break và continue
Giải thích từng dòng:
• continue: bỏ qua phần còn lại của vòng hiện tại, nhảy sang phần tử tiếp theo.
• break: thoát hẳn khỏi vòng lặp.
• Vì vậy "PASS" cuối cùng không bao giờ được in.
Kết quả mong đợi:
OK: PASS
OK: PASS
Gặp FAIL, dừng kiểm tra!
Ứng dụng: chế độ "fail fast", dừng ngay ở lỗi đầu tiên để tiết kiệm thời gian.
~~~js
const results = ["PASS", "PASS", "SKIP", "FAIL", "PASS"];

for (const r of results) {
  if (r === "SKIP") continue;
  if (r === "FAIL") {
    console.log("Gặp FAIL, dừng kiểm tra!");
    break;
  }
  console.log("OK:", r);
}
~~~

### while: lặp đến khi đạt điều kiện (retry)
Giải thích từng dòng:
• dòng 1–2: biến đếm số lần thử và trạng thái thành công.
• dòng 4: lặp khi CHƯA thành công VÀ chưa quá 3 lần.
• dòng 5: tăng số lần thử.
• dòng 6: Math.random() cho số ngẫu nhiên 0–1, giả lập một thao tác lúc được lúc không.
• dòng 9: tổng kết sau vòng lặp.
Kết quả mỗi lần chạy có thể khác nhau, đó là chủ ý. Đây là ý tưởng của "retry" trong automation.
~~~js
let attempt = 0;
let success = false;

while (!success && attempt < 3) {
  attempt++;
  success = Math.random() > 0.5;
  console.log(`Lần thử ${attempt}: ${success ? "thành công" : "thất bại"}`);
}
console.log(success ? "Xong" : "Hết lượt thử, báo lỗi");
~~~

### Lỗi thường gặp
• Lệch một (off-by-one): mảng 3 phần tử có vị trí 0, 1, 2. Dùng i < users.length chứ không phải <=.
• Vòng lặp vô hạn: quên tăng biến đếm. Nhấn Ctrl+C trong terminal để dừng, rồi thêm n++.
• Mẹo: khi không cần vị trí i, ưu tiên for...of vì không bao giờ bị lệch một.
~~~js
const users = ["an", "binh", "chi"];
for (let i = 0; i <= users.length; i++) {
  console.log(users[i]);
}
~~~

### Gọi cà phê và cầm thẻ rung
Bạn gọi một ly cà phê. Nhân viên đưa bạn chiếc thẻ rung (buzzer). Bạn không đứng chặn quầy, bạn về bàn làm việc khác. Khi thẻ rung, bạn lên lấy cà phê.
• Gọi API, mở trang web, đọc file đều mất thời gian, giống pha cà phê.
• JavaScript không đứng chờ, nó đưa bạn "thẻ rung" gọi là Promise (lời hứa sẽ có kết quả).
• await nghĩa là: "tôi đứng đợi thẻ rung rồi mới làm bước tiếp theo".

### async và await: đợi đúng lúc

• dòng 1–3: hàm wait trả về một Promise, sau ms mili giây thì "rung" (resolve). Bạn chưa cần hiểu sâu dòng 2, chỉ cần biết wait(1500) là "đợi 1,5 giây".
• dòng 5: async đánh dấu hàm có chứa thao tác cần chờ. Chỉ trong hàm async mới dùng được await.

### try/catch: bắt lỗi để chương trình không sập

• catch (error): nơi đón lỗi, error.message là thông điệp lỗi.

## LESSON programming-basics-08 | Tự viết bộ test mini: hiểu bản chất assertion

### Assertion là gì?
Assertion (khẳng định) là câu: "Tôi mong đợi X, thực tế phải đúng là X, nếu không thì báo FAIL."
Giống người kiểm hàng: đối chiếu phiếu đặt hàng (expected) với hàng thực nhận (actual).
Giải thích từng dòng:
• dòng 1: hàm nhận giá trị thực tế, giá trị mong đợi và nhãn mô tả.
• dòng 2–3: nếu khác nhau thì ném lỗi kèm thông điệp dễ hiểu.
• dòng 7–8: đúng, không có gì xảy ra, in dòng tiếp.
• dòng 9: sai, chương trình dừng với Error: Độ dài chuỗi: mong đợi 5 nhưng nhận 3.
~~~js
function assertEqual(actual, expected, label) {
  if (actual !== expected) {
    throw new Error(`${label}: mong đợi ${expected} nhưng nhận ${actual}`);
  }
}

assertEqual(2 + 2, 4, "Phép cộng");
console.log("Assertion 1 qua");
assertEqual("abc".length, 5, "Độ dài chuỗi");
~~~

### Hàm test(): chạy từng ca kiểm thử
Giải thích từng dòng:
• dòng 1: object đếm số test pass và fail.
• dòng 3: test nhận tên ca kiểm thử và một hàm fn chứa nội dung test.
• dòng 5: chạy nội dung test, await để hỗ trợ test có gọi API.
• dòng 6–7: không có lỗi nghĩa là PASS.
• dòng 8–10: có assertion ném lỗi thì ghi FAIL kèm lý do, nhưng KHÔNG làm dừng cả bộ test.
Đây chính là điều Playwright, Jest, Mocha làm cho bạn, chỉ là đầy đủ hơn.
~~~js
const summary = { passed: 0, failed: 0 };

async function test(name, fn) {
  try {
    await fn();
    summary.passed++;
    console.log(`✔ PASS  ${name}`);
  } catch (error) {
    summary.failed++;
    console.log(`✘ FAIL  ${name} -> ${error.message}`);
  }
}
~~~

### Viết test API thật
Thêm vào cùng file mini-test.js, ngay dưới hàm test và assertEqual:
Giải thích:
• Mỗi await test(...) là một ca kiểm thử độc lập, có tên rõ ràng.
• Test 2: hai lần await, một cho fetch, một cho .json().
• \n trong chuỗi là xuống dòng.
• process.exitCode = 1 báo cho hệ thống "có test fail". CI/CD dựa vào mã này để biết build đỏ hay xanh.
~~~js
const BASE = "http://localhost:3130";

async function main() {
  await test("GET /users/1 trả về 200", async () => {
    const res = await fetch(`${BASE}/users/1`);
    assertEqual(res.status, 200, "Status");
  });

  await test("User 1 có username Bret", async () => {
    const user = await (await fetch(`${BASE}/users/1`)).json();
    assertEqual(user.username, "Bret", "username");
  });

  await test("User 999 trả về 404", async () => {
    const res = await fetch(`${BASE}/users/999`);
    assertEqual(res.status, 404, "Status");
  });

  console.log(`\nTổng kết: ${summary.passed} passed, ${summary.failed} failed`);
  if (summary.failed > 0) process.exitCode = 1;
}

main();
~~~

## LESSON programming-basics-10 | Map, Set và biến đổi dữ liệu bất biến

### Tìm dòng theo mã bằng Map
Danh sách giao nhận ở trạm giả định Nếp Lam dùng id duy nhất. Lặp find cho từng mã yêu cầu tốn nhiều lượt duyệt; Map tạo chỉ mục một lần, nhưng phải quyết định xử lý mã trùng khi dựng chỉ mục.

### Set chỉ so giá trị primitive hoặc danh tính object

~~~js
const ids = ['R3','R3','R4'];
~~~

## LESSON programming-basics-11 | Promise, hủy tác vụ và kiểm soát đồng thời

### Hợp tác hủy request theo hạn chót
Trình kiểm tồn kho giả định gọi localhost:3100. Timer phát tín hiệu hủy sau hạn, còn fetch tiếp nhận signal; clearTimeout trong finally tránh giữ timer sau khi tác vụ kết thúc.
~~~js
const ctrl = new AbortController();
const timer = setTimeout(() => ctrl.abort(), 800);
try {
 const r = await fetch('http://localhost:3100/stock', {signal:ctrl.signal});
 if (!r.ok) throw new Error(`HTTP ${r.status}`);
 console.log(await r.json());
} finally { clearTimeout(timer); }
~~~

### Thu đủ kết quả khi một mục hỏng
Promise.allSettled trả trạng thái từng việc, phù hợp báo cáo kiểm nhiều file độc lập. Nó cũng không giới hạn đồng thời; tạo một nghìn Promise vẫn có thể gây một nghìn yêu cầu.
~~~js
const results = await Promise.allSettled([
 Promise.resolve({id:'L1'}), Promise.reject(new Error('invalid qty'))
]);
for (const [i,r] of results.entries())
 console.log(i, r.status, r.status === 'fulfilled' ? r.value : r.reason.message);
~~~

### Giữ giới hạn bằng worker có hàng đợi
Mỗi worker lấy một chỉ số đồng bộ trước await nên không xử lý trùng chỉ số trong một event loop. Kết quả ghi theo vị trí input dù hoàn thành khác thứ tự; lab giữ cả lỗi của từng mục.
~~~js
const input = [1,2,3,4], out = Array(input.length);
let cursor = 0;
async function work() {
 while (cursor < input.length) {
  const i = cursor++;
  try { out[i] = {ok:true,value:await check(input[i])}; }
  catch (e) { out[i] = {ok:false,error:e.message}; }
 }
}
await Promise.all([work(),work()]);
~~~

### Đừng nhầm timeout với hoàn tác
Request bị hủy ở client có thể đã được server xử lý. Với thao tác ghi, cần mã chống lặp và truy vấn lại trạng thái; không tự retry mù chỉ vì không nhận được response.

### Đo mức đồng thời thực tế
Tăng bộ đếm active trước await, giảm ở finally, lưu peak. Gây một reject và một tác vụ chậm rồi assert peak không quá hai, mọi vị trí kết quả đều có trạng thái.

PRACTICE: Viết hàm check giả trả sau 20–80 ms, trong đó một mục reject. Chạy hai worker với mười mục; bàn giao peak, thứ tự input/output và test chứng minh Promise.all không tự hủy tác vụ còn lại.
Q: Promise.all có tự hủy các công việc còn lại khi một việc reject không?
+ Không, cần cơ chế hủy riêng
- Có, luôn dừng mọi request
- Có, chỉ khi có ba Promise
Q: AbortController có hiệu lực với tác vụ nào?
+ Tác vụ thực sự đọc và xử lý signal
- Mọi vòng lặp CPU đang chạy
- Mọi Promise trong tiến trình
Q: Hàng đợi có hai worker giúp gì?
+ Giới hạn tối đa hai tác vụ đang chạy trong thiết kế đó
- Đảm bảo request nào cũng thành công
- Đảm bảo thứ tự hoàn thành

## LESSON programming-basics-12 | Fake clock, test double và kiểm thử độc lập

### Tiêm đồng hồ vào phép tính hạn
Phiếu hẹn của xưởng giả định Mầm Thoi hết hiệu lực khi now >= expiresAt. Truyền đồng hồ giúp test đúng mốc mà không phụ thuộc tốc độ máy hay việc chờ một giây thật.

~~~js
function isExpired(expiresAt, now = () => Date.now()) {

console.assert(!isExpired(100, () => 99));
console.assert(isExpired(100, () => 100));
~~~

## LESSON programming-basics-13 | Dự án: bộ kiểm hợp đồng JSON cục bộ

### Phạm vi bộ kiểm hợp đồng file
Dự án nhận đường dẫn file chứa mảng đơn nội bộ, kiểm id và qty, rồi xuất báo cáo không chứa payload gốc. Tách đọc UTF-8, JSON.parse và kiểm nghiệp vụ thành ba tầng để chỉ rõ nguồn lỗi.
~~~js
import {readFile} from 'node:fs/promises';
export async function load(path) {
 const text = await readFile(path,'utf8');
 return JSON.parse(text);
}
~~~

### Báo lỗi có vị trí để sửa đúng dòng
Trường thiếu, null và sai kiểu có thể tạo thông điệp khác nhau. Lab coi id là chuỗi không rỗng, qty là số nguyên dương; đường dẫn theo chỉ số JSON giúp người nhập tìm được mục sai.
~~~js
export function validate(rows) {
 if (!Array.isArray(rows)) return [{path:'$',code:'array_required'}];
 return rows.flatMap((x,i) => {
  if (!x || typeof x !== 'object' || Array.isArray(x))
   return [{path:`$[${i}]`,code:'object_required'}];
  const e=[];
  if (typeof x.id !== 'string' || !x.id.trim()) e.push({path:`$[${i}].id`,code:'id_required'});
  if (!Number.isInteger(x.qty) || x.qty < 1) e.push({path:`$[${i}].qty`,code:'qty_invalid'});
  return e;
 });
}
~~~

### Hợp đồng CLI và mã thoát
Báo JSON ra stdout để máy đọc, lỗi thao tác ra stderr. Không dùng process.exit ngay sau log; gán exitCode cho phép dòng ra được flush và tài nguyên được dọn theo thiết kế.
~~~js
try {
 const errors = validate(await load(process.argv[2]));
 console.log(JSON.stringify({ok:errors.length === 0,errors}));
 process.exitCode = errors.length ? 1 : 0;
} catch (e) {
 console.error(`Cannot validate input: ${e.message}`);
 process.exitCode = 2;
}
~~~

### Ma trận nghiệm thu và giới hạn
Bốn nhóm bắt buộc là hợp lệ, JSON sai cú pháp, dữ liệu sai schema, file không truy cập được. Công cụ lab chưa stream file lớn và chưa phát hiện mọi mã trùng; mô tả giới hạn thay vì gọi nó sẵn sàng sản xuất.

### Bằng chứng người khác chạy lại được
Nộp mã, fixture tự tạo, lệnh chạy với Node ESM, output và exit code. Review một lỗi từ báo cáo về chính fixture rồi sửa; chạy lại cả fixture tốt lẫn xấu để chứng minh không che lỗi.

## LESSON programming-basics-14 | Ôn tập & Thi cuối khoá

### Nền tảng và cách dùng công cụ
1. So sánh nghiêm ngặt không tự chuyển chuỗi thành số; phân biệt giá trị nhập từ form và số đã parse.
2. Giá trị trả về tạo hợp đồng kiểm được; log chỉ là bằng chứng phụ.
3. Chỉ số cuối là n-1; i <= n truy cập thêm một phần tử undefined.
4. Dữ liệu ngoài chương trình chưa đáng tin; thiếu object cha phải thành lỗi rõ vị trí.

### Dữ liệu và điều kiện biên
5. Reject đi theo luồng lỗi của async; bắt tại ranh giới có trách nhiệm xử lý.
6. Assertion phải thất bại khi kết quả khác kỳ vọng, nếu không bộ test không phát hiện hồi quy.
7. ES module có cơ chế nạp riêng; tệp .mjs hoặc package type:module giúp Node hiểu import/export.
8. Hàm ranh giới kiểm kiểu, miền và trường bắt buộc trước khi nghiệp vụ sử dụng.

### Tính đúng và cách điều tra
9. Set giữ thứ tự chèn cho các giá trị; đây là bỏ trùng primitive, không phải so nội dung object.
10. Copy mảng nông chưa copy object bên trong; tạo object mới tại chính đường cần đổi.
11. Promise.all dừng chờ kết quả thành công chung khi reject nhưng không tự ngắt các tác vụ đã bắt đầu.
12. Signal là thông báo hợp tác; fetch hỗ trợ nhưng một hàm tùy ý phải tự kiểm signal.

### Rủi ro và lựa chọn phương án
13. Giới hạn worker giảm tải đồng thời; lỗi và thứ tự kết quả vẫn cần chính sách riêng.
14. Đồng hồ được tiêm cho phép thử trước, đúng và sau hạn một cách xác định.
15. Stub nhỏ có chủ đích giúp kiểm nhánh; vẫn cần kiểm hợp đồng tích hợp để phát hiện lệch thực tế.
16. Tách tính toán thuần khỏi đọc file giúp kiểm nhanh và tái lập nhưng vẫn cần dữ liệu biên.

### Dự án, bằng chứng và bàn giao
17. Phân biệt lỗi đọc, parse và schema giúp người học sửa đúng tầng; không in dữ liệu nhạy cảm.
18. Hợp đồng có thể cho null hoặc optional riêng; dùng hasOwn để nhận biết thiếu khi cần.
19. CLI phải có trạng thái máy đọc được; thông báo dễ đọc không thay thế exit code.
20. Ma trận lỗi bao phủ các ranh giới I/O, parse và nghiệp vụ; ghi rõ output và exit code kỳ vọng.
