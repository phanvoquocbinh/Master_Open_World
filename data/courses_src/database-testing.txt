## LESSON database-testing-02 | Khóa, NULL, CHECK và toàn vẹn tham chiếu

### Constraint là hàng rào ở database
Primary/unique,NOT NULL,CHECK và foreign key bảo vệ các dạng bấtbiến khác nhau. Quyền và quy tắc qua nhiều row vẫn cần logic/transaction phù hợp;không nhét mọi yêu cầu vào một CHECK.

### Khai báo và bật foreign key trongSQLite
Bật trước transaction cho từng connection rồi đọc lại để xác nhận. Với SQLite,PRIMARY KEY dạng TEXT thông thường nên ghiNOT NULL khi cần tránh NULL theo hành vi engine,không suy giống mọi DBMS.
~~~sql
PRAGMA foreign_keys=ON;
PRAGMA foreign_keys;
CREATE TABLE classes(id TEXT PRIMARY KEY NOT NULL,capacity INTEGER NOT NULL CHECK(typeof(capacity)='integer' AND capacity>=0));
CREATE TABLE enrollments(id TEXT PRIMARY KEY NOT NULL,class_id TEXT NOT NULL REFERENCES classes(id),qty INTEGER NOT NULL CHECK(typeof(qty)='integer' AND qty>0));
~~~

### CHECK và NULL không thay nhau
CHECK(qty>0) không tự cấm NULL khi biểu thức raNULL. Thử thiếu,NULL,0,sốdương và FK không tồn tại để biết ràng buộc nào chặn;kiểu affinity của SQLite cũng cần hiểu,không mặc định type động giống schema strict.
~~~sql
INSERT INTO classes VALUES('CL7',2);
INSERT INTO enrollments VALUES('EN7','CL7',1);
-- Các câu sau là ca âm,chạy riêng và xác nhận bị từ chối:
INSERT INTO enrollments VALUES('EN8','CL7',NULL);
INSERT INTO enrollments VALUES('EN9','MISSING',1);
~~~

### Xác nhận lỗi không để lại ghi một phần
Một statement bị constraint có thể không rollback mọi statement trước trongtransaction. Testharness phải quyết định rollback theo hợp đồng,lưu số row trước/sau;không catch IntegrityError rồi commit phần đã ghi mà không chủ đích.
~~~text
before:classCL7,enrollmentEN7
negative:thử NULL/duplicate/FK
after:không có record âm,mọi invariant giữ
transaction policy:chốt cho lô dữ liệu
Error evidence dùng id giả và code phù hợp.
~~~

### Dialect và connection là điều kiện test
Ghi SQLite version,cấu hình và schema trongmanifest. Một test chạy ở DBMS khác hoặc connection quên PRAGMA có thể cho kết quả khác;report cần đủ điều kiện,không gọi tool sai tùytiện.

PRACTICE: Nộp constraint matrix10 ca với NULL,unique,CHECK và FK,bằng chứng before/after. Kiểm hai connection độc lập về foreign_keys,có rollback theo chính sách lô lab.
Q: CHECK(qty>0) có tự cấm NULL trongSQLite không?
+ Không,cần NOT NULL nếu bắt buộc
- Có luôn
- Chỉ khi có ORDER BY
Q: SQLite foreign keys cần kiểm cấu hình gì?
+ Bật và xác nhận cho từng connection phù hợp
- Chỉ khai báo một lần trên giấy
- Không bao giờ cần bật

## LESSON database-testing-03 | Đối soát số lượng và tổng nghiệp vụ

### Count bằng nhau có thể vẫn sai
Mất EN7 và thêm EN8 giữ count nhưng đổi nghiệp vụ. Đối soát cần khóa,giá trị,tổng theo trạng thái và sai khác có vị trí;chọn invariant có ý nghĩa,không chỉ tạo nhiều SUM ngẫu nhiên.

### Tìm id mất và id dư bằng EXCEPT
Hai bảng before/after tronglab giúp so tập id. Phép tập không giữ multiplicity như đếm trùng,nên cần kiểm duplicate riêng trước khi suy tập bằng nhau là đủ.
~~~sql
SELECT id FROM expected_enrollments EXCEPT SELECT id FROM actual_enrollments;
SELECT id FROM actual_enrollments EXCEPT SELECT id FROM expected_enrollments;
SELECT id,COUNT(*) FROM raw_enrollments GROUP BY id HAVING COUNT(*)>1;
~~~

### Nhóm đúng grain trước join
Payment_attempt có paid/failed và nhiều row trên enrollment. Chỉsum paid theoenrollment rồi join đích;không SUM enrollment.total sau join trực tiếp hoặc SUM DISTINCT như cách vá chung.
~~~sql
WITH p AS(
 SELECT enrollment_id,SUM(amount_minor) AS paid
 FROM payments WHERE status='paid' GROUP BY enrollment_id
) SELECT e.id,e.total_minor,COALESCE(p.paid,0) AS paid
FROM enrollments e LEFT JOIN p ON p.enrollment_id=e.id
WHERE e.status='paid' AND COALESCE(p.paid,0)<>e.total_minor;
~~~

### Đối soát theo nhóm để thấy lệch
Tổng toàn cục có thể khớp dù phân loại trạng thái sai. So count,money và unique theo ngày/status/currency khi đúng hợp đồng;không cộng các currency hoặc đơn vị khác nhau.
~~~text
by status:count,distinctid,summinor
by date:ngày nghiệp vụ đã chốt
by currency:không trộn tiền
rowdiff:field thay đổi theoid
Expected viết độc lập,không copy actual.
~~~

### Đủ fixture để kiểm checker
Một query trả rỗng trên dữ liệu sạch không chứng minh đúng. Cài mất,dư,trùng,sai amount và sai status có chủ đích;checker phải chỉ đúng id/lý do,tránh report toàn lỗi chungchung.

PRACTICE: Tạo before/after có count bằng nhau nhưng mất/dư/trùng và sai tiền. Nộp tám phép đối soát,expected theoid và giải thích grain/NULL/currency.
Q: Đối soát COUNT trước/sau bằng nhau chứng minh đủ chưa?

- Đủ vì dữ liệu bằng nhau

## LESSON database-testing-04 | Mapping ETL và quy tắc biến đổi

### Mapping là hợp đồng biến đổi
Nguồn CSV của Thoi Mầm có student_code,class_code,qty_text và amount_text. Ghi target,kiểu,đơn vị,nullable,normalization và rule lỗi;không đổi tên cột rồi xemETL đã đúng.

### Ma trận nguồn-đích có ví dụ
Một dòng mapping cần case tốt/âm và lineage. Chính sách trim,UnicodeNFC hoặc default chỉ được áp khi đã chốt,không tự bỏ dấu hoặc biến chuỗi rỗng thành0.
~~~text
source qty_text ->target qty INTEGER
rule:số nguyên dương,chỉ parse theoformat lab
empty/null ->reject codeQTY_REQUIRED
invalid ->reject codeQTY_FORMAT
lineage:batch/sourceLine->targetId hoặc quarantine
~~~

### Hàm biến đổi nhỏ kiểm được
Ví dụ Python dùng Decimal để đọc đơn vị tiền lab có hai sốlẻ,không float nhân100. Chính sách ROUND_HALF_UP là giả định của bài,cần đúng yêu cầu từng currency thật ở bối cảnh khác.
~~~python
from decimal import Decimal,ROUND_HALF_UP
def to_minor(text):
 value=Decimal(text)
 if not value.is_finite() or value<0:raise ValueError('amount_invalid')
 return int((value*100).quantize(Decimal('1'),rounding=ROUND_HALF_UP))
assert to_minor('1.235')==124
~~~

### Lineage giữ lý do loại hoặc chuẩn hóa
Báo raw value có thể nhạy cảm,nên lab dùng chuỗi giả và chỉ giữ field cần thiết. Nếu sửa dữ liệu được phép,ghi rule/version và kết quả;đừng làm thay đổi âmthầm khiến không truy nguồn được.
~~~text
sourceLine3.qty_text=" 2 "
policy:trim được phép ->qty 2
sourceLine4.qty_text="hai"
policy:reject ->QTY_FORMAT
Không convert mọi lỗi thành0hoặc skip imlặng.
~~~

### So expected bằng bảng tay
Với mười dòng nhỏ,tính expected độc lập trước chạy pipeline. Dùng cả case có thể quan sát normalization và error,không tính expected bằng chính hàm transform đang kiểm.

PRACTICE: Nộp mapping cho sáu trường,mười fixture với lineage và expected tay. Kiểm trim/Unicode/amount/null theo chính sách,có quarantine rõ khi từ chối.
Q: Mapping ETL cần nêu gì ngoài tên trường?
+ Kiểu,đơn vị,quy tắc,nullable và nguồn
- Chỉ alias đẹp
- Chỉ độ dài file
Q: Chuẩn hóa chữ/tên nên làm theo gì?
+ Quy tắc nghiệp vụ đã chốt và giữ dấu vết cần thiết
- Luôn bỏ mọi dấu

## LESSON database-testing-05 | Dữ liệu trùng, thiếu và sai kiểu

### Trùng khóa có thể là nhiều ý nghĩa
Hai event cùng id có thể là retry,update version mới hoặc conflict cùng version. Quyết định theo khóa,version và payload hash đã chốt;đừng luôn last-write-wins theo giờ nhận.

### Bộ case phân loại rõ
Nhận event version1 lần đầu,lặp lại cùng payload,version2đổi hợp lệ và version1đến muộn. Cùng version khác payload nên quarantine/raise theo hợp đồng,không ghi đè imlặng.
~~~text
E1,v1,payloadA ->insert
E1,v1,payloadA ->no-op nếu retry
E1,v2,payloadB ->update hợp lệ
E1,v1,payloadA sauv2 ->không hạ version
E1,v2,payloadC ->conflict theo rulelab
~~~

### Thiếu/null/sai kiểu là chiều riêng
Staging raw có thể chứa mọi input để báo lỗi,còn đích giữ constraint. Việc một field thiếu khác null có thể ảnh hưởng default/patch semantics,nên expected phải được chốt và kiểm riêng.
~~~json
{"id":"E1","qty":2}
{"id":"E2"}
{"id":"E3","qty":null}
{"id":"E4","qty":"2"}
Bốnrecord cầnexpected theo mapping,khôngcoi tấtcả tựparse.
~~~

### Quarantine có tổng đối soát
Giữ sourceLine,field,code và định danh giả,đủ người sửa truy được. Số accepted/rejected/deduplicated phải giải thích tổng input;không để dòng mất không dấu vì catch lỗi rồi continue.
~~~text
input10 =accepted7 +rejected2 +duplicate1
error:{line4,path:qty,code:QTY_REQUIRED}
error:{line8,path:id/version,code:CONFLICT}
Dữ liệu riêng tư thật không được đưa vào fixture/report.
~~~

### Kiểm hậu quả không chỉ error text
Saurow bị từ chối,đích không đổi ngoài ý muốn,batch status và checkpoint đúng. Nếu allowpartial,cần report rõ;all-or-nothing cần rollback và bằng chứng tác dụng cuối.

PRACTICE: Tạo12event với retry/update/conflict/thiếu/null/sai kiểu,expected từng line. Nộp target snapshot,quarantine và đối soát input/output có mẫu số rõ.
Q: Hai dòng cùng khóa khác payload cần xử lý sao?
+ Theo quy tắc xung đột,có evidence
- Luôn lấy dòng cuối không báo
- Luôn cộng mọi trường
Q: Dữ liệu bị quarantine nên giữ gì?
+ Vị trí nguồn,lý do và thông tin tối thiểu để sửa
- Mọi bí mật thật
- Chỉ bỏ dòng

## LESSON database-testing-06 | Thời gian, múi giờ và tiền tệ

### Instant và ngày địa phương khác nhau
Timestamp có offset mô tả thời điểm,còn ngày báo cáo có thể theo nơi nghiệp vụ. Chốt timezone,format và precision;không cắt phần ngày UTC rồi xem đúng với mọi báo cáo.

### Chuyển giờ bằng datetime aware
Ví dụ tự viết dùng offset giả cho fixture,không tên địa danh thật. Chuỗi thiếu offset cần policy,tránh astimezone trên naive làm phụ thuộc timezone máy chạy.
~~~python
from datetime import datetime,timezone,timedelta
instant=datetime.fromisoformat('2030-01-01T23:30:00+00:00')
local=instant.astimezone(timezone(timedelta(hours=7)))
assert local.date().isoformat()=='2030-01-02'
~~~

### Tiền có currency và quy tắc làm tròn
Lab lưu minor unit nguyên và currencyDLM giả. Cộng total chỉ trong cùng đơn vị,có rule về làm tròn tổng hay từng dòng;hai cách có thể lệch dù đều tính đúng công thức riêng.
~~~text
price105minor,qty 3,discount10%
lab rule:round-half-up trên discount tổng
315*10%=31.5 ->32minor
net283minor
Rule khác ->expected khác,cần version.
~~~

### Case biên thời gian và decimal
Thử quanh nửa đêm,offset khác,cùng instant khác chuỗi và số gần ngưỡng làm tròn. Không dùng float expected để kiểm Decimal,cũng không trộn precision cao và format hiển thị.
~~~text
time:trước/đúng/sau ranh ngày nghiệp vụ
source:thiếu offset,sai format,precision khác
money:1.234/1.235/1.236 theo rulelab
currency:mismatch phải được phân loại
Expected tính độc lập và ghi đơn vị.
~~~

### Ghi môi trường có ảnh hưởng
Timezone database/runtime,cấu hình locale và schema version có thể đổi parse/format. Manifest phải đủ để tái hiện;không đổi toàn máy công việc chỉ để thử lab,khoanh trongharness/fixture.

PRACTICE: Viết12 ca timestamp/money có ngày biên,offset và rounding,có hai currency giả. Nộp expected instant/date/minor,rule/version và một ví dụ sai khi cắt ngày UTC.
Q: Tiền nên kiểm đơn vị thế nào?
+ Currency,minor unit và quy tắc rounding
- Chỉ nhìn số có dấu chấm
- Luôn dùng float equals
Q: Timestamp không có offset cần gì?
+ Chính sách timezone rõ trước quy đổi
- Tự xem là UTC ở mọi nơi
- Cắt hết phần giờ

## LESSON database-testing-07 | Migration tiến lùi và tương thích

### Migration đổi cấu trúc và nghĩa dữ liệu
Thêm currency cho đơn cũ cần biết giả định backfill có đúng không. App đọc/ghi trong cửa sổ chuyển đổi có thể dùng schema khác,phải kiểm compatibility và thứ tự rollout theo kế hoạch lab.

### Thử trên bản sao có fixture cũ
Snapshot before có pending/confirmed/cancelled và row biên. Chạy migration trên filecopy,đối soát id,tiền,status và constraint;không thử đầu tiên trên dữ liệu đang dùng.
~~~text
before:LABschema1,snapshot hash được ghi
apply:migrationM2
after:rowcount,key,amount/status/currency đúng
appcompatibility:reader/writer theo version hỗ trợ
backup restore được thử,trong phạm vi filelab
~~~

### Ví dụ thêm field có backfill minh bạch
SQLite lab thêm field nullable rồi backfill theo giả định toàn đơn cũ dùngDLM. Nếu muốn NOT NULL thật,cần migration phù hợp engine và dữ liệu;không gọi bước UPDATE là đã áp constraint mới.
~~~sql
BEGIN;
ALTER TABLE orders ADD COLUMN currency TEXT;
UPDATE orders SET currency='DLM' WHERE currency IS NULL;
SELECT COUNT(*) FROM orders WHERE currency IS NULL;
COMMIT;
-- Ràng buộc NOT NULL mới cần bước schema riêng theo engine và kế hoạch đã kiểm.
~~~

### Rollback không tự lấy lại thông tin
Xóa column có thể mất giá trị đã nhập,còn row mới saumigration không có trong backup cũ. Chốt điểm dừng ghi,phục hồi và reconciliation,gồm khả năng chuyển ngược có giới hạn.
~~~text
failure points:giữa DDL/backfill/constraint
expected:rollback/restore theo từng giai đoạn
new writes:giữ/chuyển/đối soát có policy
verify:không mất/trùng và app còn đọc được
Không hứa rollback mọi thay đổi đều tự động an toàn.
~~~

### Lần chạy lại cần expected riêng
Migration có version/checksum,nếu đã áp thìno-op hoặc báo đã áp theotool. Không catch mọi SQL error rồi đánh thành công,cũng không áp lại UPDATE làm ghi đè dữ liệu mới không chủ đích.

PRACTICE: Nộp migration test plan với fixture schema cũ,backfill,appcompatibility và ba failurepoint. Thử restore trên filecopy,đối soát id/tiền/status và ghi khả năng rollback còn thiếu.
Q: Migration cần kiểm gì về dữ liệu cũ?
+ Giữ nghĩa,backfill,ràng buộc và đối soát
- Chỉ schema tạo được
- Chỉ tên cột mới
Q: Rollback schema có luôn khôi phục dữ liệu đã mất không?
+ Không
- Có luôn
- Có nếu xóa column

## LESSON database-testing-08 | CDC, watermark và dữ liệu đến muộn

### Event time và vị trí đọc khác nhau
CDC mô phỏng của Thoi Mầm có sourceSeq tăng theo log và occurredAt theo sự kiện. Dòng đến muộn có thể mang thời gian cũ nhưng vị trí log mới;đừng dùng một timestamp thay mọi ý nghĩa thứ tự.

### Cursor theo hợp đồng nguồn
Nếu nguồn chỉ có updatedAt,cặp thời gian/id giúp phân xử tie trong điều kiện đã chốt,chưa giải mọi update/lateness. Với log CDC,cần position,retention,snapshot ban đầu và delete/tombstone theo hợp đồng.
~~~text
sourceSeq41:EN7,v1,occurredAt ngày2
sourceSeq42:EN8,v1,occurredAt ngày1 đến muộn
sourceSeq43:EN7,v2,delete
Checkpoint43 nghĩa đã áp đầy đủ tới vị trí đó
Không dùng occurredAt ngày2đểbỏseq42.
~~~

### Lookback cần dedup và giới hạn
Với timestamp polling,đọc chồng window để bắt một phần lateness rồi upsert theo khóa/version. Chốt cửa sổ và cutoff/snapshot;dòng muộn quá window vẫn có thể sót,nên cần reconciliation phù hợp,chưa đủ để hứa không mất tuyệt đối.
~~~sql
SELECT id,version,updated_at,payload FROM source_rows
WHERE updated_at>=:lookback_start AND updated_at<:cutoff
ORDER BY updated_at,id;
-- Tham số được cấp bởi harness lab;cutoff vàwindow được ghi.
~~~

### Delete không để event cũ hồi sinh
Nếu nguồn có version theoentity,giữ tombstone hoặc cơ chế tương đương để chặn upsert version cũ saudelete. Version phải có nghĩa đã cam kết,cùng version khác payload cần conflict handling trước áp dụng.
~~~text
EN7 v1 insert ->live
EN7 v3 delete ->deleted,tombstone v3
EN7 v2 update đến muộn ->không hồi sinh
EN7 v3 khác payload ->conflict theo policy
Không tin thứ tự giờ nhận là thứ tự nghiệp vụ.
~~~

### Thiết kế ca có timestamp trùng và dữ liệu đến muộn
Fixture có hai id cùng timestamp,một update cùng id,một delete và event muộn ngoài window. Nêu kết quả trong phạm vi bảo đảm của nguồn và case cần đối soát toàn bộ định kỳ;không đổ mọi missing vào SQL mà không xem contract.

PRACTICE: Tạo mười event CDC giả với tie,late,delete vàout-of-order. Nộp cursor/checkpoint expected sau từng batch,giới hạn lookback và đối soát phát hiện dữ liệu ngoài window.

## LESSON database-testing-09 | Idempotency và chạy lại pipeline

### Rerun là tình huống bình thường
Job ETL có thể crash sau ghi đích trước ghi checkpoint hoặc nhận lại cùng batch. Thiết kế mục tiêu idempotent trên tác dụng,không nhất thiết chỉ một request;mỗi điểm dừng cần expected phục hồi.

### Upsert theo version nhưng kiểm conflict trước
SQLite ON CONFLICT minh họa nhận bản mới hơn theoid;version bằng payload khác phải được phát hiện trước đoạn này. Nó không tự đảm bảo mọi quy tắc hoặc checkpoint nếu hai việc nằm transaction khác.
~~~sql
INSERT INTO target_rows(id,version,qty,deleted) VALUES(:id,:version,:qty,:deleted)
ON CONFLICT(id) DO UPDATE SET
 version=excluded.version,qty=excluded.qty,deleted=excluded.deleted
WHERE excluded.version>target_rows.version;
~~~

### Đích và checkpoint cùng transaction khi phù hợp
Lab một SQLite file có thể commit thay đổi đích và checkpoint cùng connection. Với hệ phân tán khác,kế hoạch atomicity/recovery có thể cần thiết kế khác,không giả định transaction phủmọi nơi.
~~~python
with conn:
 for row in validated_batch:
  conn.execute(upsert_sql,row)
 conn.execute('UPDATE checkpoints SET position=? WHERE job=?',(last_position,'LAB-ETL'))
# conn,upsert_sql vàfixture được khởi tạo theo hợp đồng lab.
# Exception phải lanra để context manager rollback.
~~~

### Crash matrix kiểm trạng thái cuối
Chèn failure hook chỉ tronglab ở trước ghi,giữa rows và trước/sau commit. Khởi động lại,đọc đúng checkpoint và rerun;assert target bấtbiến,không trùng và quarantine vẫn truy được.
~~~text
C1 beforewrite ->target/checkpoint cũ
C2 giữa batch ->rollback theo chính sách all-or-nothing
C3 trước commit ->cảhai chưa commit
C4 saucommit nhưng trước ack ->rerun không nhân tác dụng
Số record/phiên bản phải được đối soát.
~~~

### Không bỏ lỗi để job xanh
Catch rồi continue có thể làm checkpoint vượt dòng chưa áp dụng. Nếu partial processing,định nghĩa cách đánh dấu và retry từng row rõ;report không được gọi đủ lô khi còn dòng không có quyết định.

PRACTICE: Thử cùng batch ba lần và bốn crashpoint trên lab SQLite. Nộp target/checkpoint trước/sau,reconciliation và conflict cùng version;chỉ dùng filecopy có backup.
Q: Chạy lại cùng batch nên giữ bất biến gì khi yêu cầu idempotent?
+ Không nhân record hoặc tác dụng
- Mỗi lần luôn thêm bản copy
- Luôn trả200
Q: Lỗi giữa ghi đích và checkpoint có rủi ro gì?

Q: Mapping ETL cần nêu gì ngoài tên trường?
